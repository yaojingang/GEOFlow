**GEOFlow 文章内链管理最终方案（待确认）**

日期：2026-09-13。适用范围：主站后台「网站设置」及文章详情页。本文件替代上一轮聊天中的方案，当前完成的是设计复审和文档编写，业务功能尚未实施。

建议交付「相关文章 + 随机推荐」两个独立区块，采用可配置周期、访问触发和后台限量刷新。相关文章默认保留 1 小时，随机推荐默认保留 24 小时。到期表示可以申请更新；有访问时才触发，后台完成后原子替换结果。无人访问的文章不按周期重算。缓存清空、应用重启和爬虫身份均不主动改变仍有效的随机批次。文章下架、删除、权限变化和两区去重具有更高优先级。

这里的 1 小时和 24 小时是默认产品取舍，15 分钟相关更新保留为可选项。Google 的官方资料说明了链接发现、抓取需求和服务器响应之间的关系，没有规定推荐区应采用这些时间值，也没有提供“每次换链接即可提高收录”的保证。[Google 链接实践](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)、[抓取预算说明](https://developers.google.com/crawling/docs/crawl-budget)

**刷新周期、触发时机和处理速度分别控制，避免蜘蛛集中访问带来计算峰值。**

| 情况 | 文章请求中的动作 | 后台动作 |
| --- | --- | --- |
| 推荐仍有效 | 读取名单，批量核实公开状态，直接输出 | 无 |
| 推荐到期且有人访问 | 输出仍有效的旧条目，只申请一次刷新 | 在限量队列中重建并替换 |
| 推荐到期但无人访问 | 无请求、无动作 | 不为该文章生成新名单 |
| 首次访问或相关缓存被清理 | 相关文章临时使用同分类的轻量列表；随机区没有已有批次时暂时隐藏 | 按限额准备完整结果 |
| 同一篇文章同时被大量访问 | 复用旧结果，刷新申请按文章和类型去重 | 同一种结果只允许一个有效重建任务 |
| 蜘蛛同时访问很多不同文章 | 优先保留正文访问和已有有效链接，超过接纳额度的刷新暂缓 | 全站限速处理，避免多篇文章同时重建 |

同分类临时列表按站点、分类缓存 1 小时，缓存缺失时仅执行一条有数量上限的同分类索引查询，输出仍重新核实公开状态。当前文章排除及两区去重照常执行。冷启动允许相关区暂时只反映分类关系；首批完整结果由后台补齐。没有可用同分类文章时隐藏该临时区块。

首版刷新保护采用内部默认值：全站同时最多 1 个推荐计算任务，每分钟最多接纳 30 个文章结果刷新任务，待执行和执行中的推荐任务合计最多 100 个。限额跨来源文章和应用节点生效，不按访客分别计算。超过额度时本次申请直接暂缓，后续访问再尝试；没有成功入队时不标记为已排队。按文章设置 60 秒申请冷却，重复命中不延长冷却。候选池准备优先于依赖它的随机刷新，历史回填和对账分块执行，并共用单个推荐后台计算名额。

上述保护值在内部配置集中管理，压测后可以调整；后台首版只开放两个时间周期，避免把任务调度参数交给内容运营者维护。刷新耗时、失败、排队数量和等待时间进入内部诊断。队列故障或蜘蛛持续访问海量页面时，更新可能延后；界面区分“到期可刷新”“等待刷新”和“已更新”，不会把到期时间显示为完成时间。

**这轮复审补齐了缓存、更新和模板接入的具体边界。**

| 上一版需要补齐的地方 | 最终决定 |
| --- | --- |
| “按天随机”容易被理解为全站凌晨统一刷新 | 按每篇文章首次成功生成批次的时间计时，到期后通过访问申请后台轮换；无访问的页面不后台反复重算 |
| 相同种子配合变化中的候选集，重新计算仍可能得到不同结果 | 把随机批次名单保存到数据库，普通缓存失效后读回这一批名单 |
| 新文章发布后，进入推荐的时机不明确 | 关键词索引随正常写入同步更新；已有结果到期、有访问且后台完成刷新后参与新选择；候选池按变化和需求更新 |
| 缓存里的文章可能已下架或改地址 | 输出前实时检查公开状态、读取当前标题并生成正式 URL；不缓存完整推荐 HTML |
| 批量操作可能绕过模型事件 | 普通写入和批量写入都接入索引维护，单独覆盖 API、CLI、后台批量操作及任务生成等入口 |
| 全局版本每次发布都增长，会让大量文章一起失效 | 推荐缓存按来源文章和规则识别；新增文章通过所选周期参与后续排序，不因每篇新文清空全站结果 |
| 高并发下可能同时生成多批随机结果 | 同一站点、来源文章使用数据库唯一约束及短期生成租约，完成后原子替换名单 |
| 缓存后还有整页缓存或 CDN | 文章 HTML 在应用层明确输出 `Cache-Control: no-store`；外层缓存配置纳入部署验收 |
| 已有浏览计数可能推进文章更新时间 | 本轮源码检查确认此调用链会更新 `updated_at`；本次实施修正计数写入，避免访问量驱动推荐失效和 sitemap 更新时间变化 |
| 外部模板有卡片，不代表文章页有推荐挂载点 | 同时检查模块契约和实际渲染；缺少接入点时先适配模板，再启用新机制 |

以上发现来自当前源码和官方文档检查。尚未执行本功能的运行测试、压力测试或线上抓取验证。

**后台沿用现有网站设置的入口与视觉风格。**

在网站设置的运营管理区域增加「内链管理」入口，进入独立编辑页。设置一次保存，不与网站基础信息表单混合提交。保存时校验权限、CSRF 和字段范围，校验失败保留输入；成功后记录操作日志。

| 设置项 | 默认建议与限制 |
| --- | --- |
| 文章内链总开关 | 控制本功能输出的两个区块 |
| 相关文章 | 可独立开启，默认标题「相关文章」，默认 6 篇，允许 1 至 6 篇 |
| 随机推荐 | 可独立开启，默认标题「更多阅读」，默认 4 篇，允许 1 至 6 篇 |
| 标题编辑 | 普通文本，最多 40 个字符；空值使用当前语言的默认标题 |
| 排列顺序 | 正文及标签之后先放相关文章，再放随机推荐，最多 12 个推荐条目 |
| 样式 | 固定为「跟随当前模板」，颜色、字体、列数由模板负责 |
| 相关文章更新周期 | 默认 1 小时，可选 15 分钟、1 小时、6 小时、24 小时 |
| 随机推荐轮换周期 | 默认 24 小时，可选 6 小时、12 小时、24 小时、72 小时、7 天 |
| 刷新方式 | 固定为「到期后有访问才申请后台刷新」，页面说明等待期间仍展示有效旧结果 |
| 文章预览 | 从当前站点已发布文章中选择，显示实际推荐、相关依据、批次生成时间、可刷新时间及等待状态 |
| 模板状态 | 显示「支持内链模块」或「需要适配」，同时说明缺少的接入能力 |

未保存新设置的旧站继续使用原有相关文章逻辑，避免升级本身改变正在展示的页面。首次编辑的建议值为“相关开启、随机关闭”；保存后转入新管理机制。显式关闭总开关后，支持该契约的模板停止输出两个区块，保留配置以便恢复。

新规则首次启用时，在配置事务提交后派发一次维护任务，准备关键词索引；随机区开启时同时准备候选池。周期维护负责接续未完成或漏派发的准备工作，单篇推荐由访问按需申请。关键词索引或单篇结果准备期间，相关文章使用同分类的稳定列表。后台显示准备状态，文章正文保持可访问。

预览使用独立请求上下文和未保存的表单配置，复用现有受限预览能力。预览不会改变线上随机批次、启用主题、文章浏览量或推荐缓存。预览中的“查看另一批示例”只生成临时示例；实际保存后以线上批次为准。预览响应禁止缓存与索引。

**两种推荐先经过统一的文章资格检查。**

候选来源必须经过 `SiteScopedArticleQuery` 的当前站点可见范围，再排除当前文章、已删除记录、草稿及非公开记录。未来发布时间尚未到达的文章不进入新推荐模块；历史已发布且发布时间为空的记录沿用其创建时间。

首版只在主站启用新机制。托管站保留现有行为和隔离规则，主站设置不自动同步到托管站或外部分发站。数据键明确带 `primary` 站点范围，后续扩展需要按站点分别管理。

统一以文章 ID 去重，并在输出时防止重复正式 URL。重复标题本身不构成合并依据。模板不自行查询数据库、抽样或拼接文章路径。查询只加载本次展示所需的字段与关联，空区块连同标题一起隐藏。

**相关文章按关键词和分类排序，更新内容时重新评估。**

关键词来自现有 `original_keyword` 和 `keywords`。前者作为一个完整词条，后者按中英文逗号、顿号和换行拆分；统一前后空白、连续空格、英文大小写，去重后最多保留 12 个词条。保留完整词语进行匹配，避免把 `AI` 和 `AIO` 当作同一个词。

排序按以下优先级执行：

1. 有共同关键词的文章优先，共同关键词数量降序。
2. 共同关键词数量相同时，同分类文章优先。
3. 再相同时，按有效发布时间降序、文章 ID 降序排列。
4. 数量不足时，追加同分类文章，仍按有效发布时间与 ID 排序。

没有共同关键词、也没有同分类候选时，允许少显示或隐藏；跨主题探索交给独立随机区。关键词属于精确匹配，首版不进行同义词推理、正文语义分析或大模型调用。

相关文章缓存一次保存最多 18 个候选 ID，其中包含补位候选，不保存最终标题、URL 或 HTML。每次输出重新计算这些候选与当前文章的关键词、分类匹配关系，移除已经不相关的结果，并按当前规则取前 N 篇。候选耗尽时允许少显示，后台刷新时重新检索完整候选范围。

缓存的正常有效期由管理员选择，默认生成后 1 小时，命中不会延长这个时间。到期后的访问只申请后台重排；即使重算后仍是同一组文章，也视为正常结果。当前文章关键词或分类修改后，通过来源特征变化识别过时结果，实时移除旧名单中已不相关的条目，并申请刷新；完整排序在后台完成。其他文章的新建或修改，在既有页面到期、有访问且刷新完成后参与重新评估。

此方向借鉴 Ghost 的标签关联和主题卡片复用，以及 Hugo 的索引匹配与稳定排序。实现使用 GEOFlow 现有数据和模板，不接入它们的运行服务。[Ghost 官方示例](https://ghost.org/tutorials/read-next/)、[Hugo 相关内容实现](https://github.com/gohugoio/hugo/blob/master/related/inverted_index.go)

**随机推荐保存固定批次，定期换批，并处理小样本重复。**

每篇文章独立生成随机批次。批次保存展示 ID、补位 ID、生成时间、可轮换时间和规则版本。正常情况下，从生成起按设置保留一段时间，默认 24 小时；到期后的访问申请后台换批，完成前可继续展示经过校验的旧名单。同一时段内普通访客和蜘蛛读到相同的名单，不依据 User-Agent、IP、Cookie、请求次数或查询参数改变推荐。

| 访问情形 | 预期行为 |
| --- | --- |
| 蜘蛛在 10 分钟后再次访问同一篇文章 | 当前随机批次保持一致 |
| 默认周期下，蜘蛛在批次生成 25 小时后再次访问 | 本次请求申请后台刷新并读取经校验的旧批次；后台完成后，后续请求看到新批次 |
| 蜘蛛访问另一篇文章 | 使用该文章自己的随机批次；小站候选有限时允许部分重合 |
| 页面一周无人访问 | 不补算这一周的每日名单；下次访问申请生成一个当前批次，超过旧结果保留上限时暂时隐藏随机区 |
| 清空 Laravel 缓存或应用重启 | 从数据库恢复当前批次，在有效期内保持原名单 |
| 新文章发布 | 标记候选池待更新，有抽样需求时更新；已有有效批次继续保留，后续轮换时有机会选中 |
| 当前批次中有文章下架 | 下一次输出即移除，并按固定补位次序补位 |
| 相关文章更新，与随机区产生重复 | 相关文章优先，随机区补位；剩余有效条目的相对顺序保持不变 |
| 只修改标题或切换到另一款兼容主题 | 名单与原轮换时间保持不变，只改变展示 |
| 修改某个区块的推荐数量或选择规则 | 对应区块按新规则生效；相关区变化对随机区只做必要的去重补位 |

每次换批先排除当前文章、本次相关区展示文章和上一批已经展示的随机文章。在剩余候选足够时，新的随机名单与上一批完全不同；不足时优先使用新候选，再从上一批仍有效的文章补足。站内可用文章很少时允许重复，数量和轮换效果如实展示。

批次除最多 6 个展示 ID 外，再保存最多 18 个补位 ID。下架和两区冲突先按固定次序使用已有补位名单；耗尽时前台少显示，并申请后台从当前候选池补位，原有 `rotate_after` 不顺延。换批和补位共用同一条记录的生成租约及版本检查，防止并发覆盖。新的补位文章可能来自本周期内刚发布的文章，这是内容变化带来的例外，不影响其他有效条目。

例如：默认设置下，某页周日 10:20 生成一批随机推荐，周一 10:20 起可以申请轮换。若周一 11:00 才有访问，本次请求提交申请并返回有效旧名单；后台完成后，后续访问看到新名单。周日 14:00 发布的文章在候选池更新后可以参与下一轮抽样。每个新批次从实际生成时间重新计时。

随机推荐增加历史文章的展示机会，无法保证每篇文章获得曝光或被蜘蛛访问。首版继续依靠分类分页和 sitemap 提供稳定的全站发现入口，推荐链接作为补充。后台及文档不把随机曝光等同于收录效果。[Google 内链与发现说明](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)

**缓存分层保存，时间边界各自独立。**

| 层次 | 保存内容 | 时间与更新规则 |
| --- | --- | --- |
| 内链配置 | 一条 `site_settings` JSON 配置 | 每个文章请求直接读取一次本功能配置并在请求内复用，避免不同节点的本地设置缓存拖延关闭操作 |
| 关键词索引 | 文章与规范关键词关系 | 持久化派生数据，关键词写入同步维护；历史数据分批构建 |
| 相关文章结果 | 最多 18 个候选 ID 及生成时间 | 正常有效期 R，默认 1 小时；物理保留至生成后 2R；到期有访问才申请重建 |
| 随机候选池 | 当前站点已发布文章 ID 的分块快照 | 初次启用、池缺失，或内容变化且存在抽样需求时更新；正常整池重建最短间隔 15 分钟，无变化不重建 |
| 随机推荐批次 | 当前展示 ID、补位 ID、批次时间 | 数据库保存，正常有效期 T，默认 24 小时；到期有访问才申请轮换；缓存清空不删除这一层 |
| 展示数据 | 当前标题、公开状态、分类、必要的卡片字段及正式 URL | 在本次请求中批量读取与生成，不跨请求缓存整段 HTML |
| 文章整页 HTML | 页面及推荐链接 | 首版不增加整页缓存，在应用响应层明确设置 `no-store` |

相关文章缓存标识包含算法版本、站点范围、来源文章 ID、来源关键词与分类特征及相关区数量，并保留该文章最近一次名单供实时重验后的过渡展示。随机批次的选择版本由随机算法版本和随机区数量组成，相关区的启停和数量变化通过输出去重及补位处理。总开关或随机区关闭期间保留现有批次，重新开启时按当前周期判断是否到期。标题文案、模板 ID、浏览量、IP、User-Agent、请求参数和文章通用 `updated_at` 均不参与候选名单的缓存标识。改变模板时，展示由新的模板重新渲染。

修改周期时不清空全站结果，也不批量派发任务。以各结果原生成时间加新的 R 或 T 重新判断可刷新时间；缩短周期后已经到期的页面，等下一次访问限量申请刷新。延长相关周期后，已被缓存存储回收的名单无法恢复，使用同分类临时列表并申请重建。随机名单仍可从持久记录读回，周期调整不重新抽样。

随机候选池按文章 ID 排序，以每块 500 个 ID 保存，头信息只记录代号、数量、分块数和构建时间。抽样先随机选择编号位置，再批量取所需块，避免按来源文章排序整个候选集，也避免从稀疏的文章 ID 数值区间抽样造成偏差。选择使用局部随机源，随后把实际结果保存为批次；可见资格仍由输出时的数据库查询决定。

新候选池先完整写入分块，再发布头信息；读取不到所需分块时放弃该次新池读取。当前代不设置定时过期，按需换代后为旧代设置 1 小时回收期；缓存存储仍可能主动逐出当前代，缺失时按需重建。内容发布、下架、恢复等操作只标记池已变化，多次修改合并处理。维护任务同时检查变化标记和未满足的抽样需求，正常两次整池构建至少相隔 15 分钟；首次或池缺失可提前恢复，但同站点始终只允许一个池构建任务。缓存中断期间不把不完整池发布为可用池，也不在每个文章请求里重新加载全库。

这套设计增加两张派生表，普通缓存继续使用项目配置的 Laravel Cache。源码中的默认 Cache Store 为 `database`，本方案不要求新增 Redis。随机批次的一致性由共享应用数据库保证；候选池的构建互斥采用现有缓存锁，多个独立本地缓存节点可以各自维护候选池，但只能通过同一个数据库批次记录发布最终名单。[Laravel 缓存与锁的边界](https://laravel.com/framework/docs/12.x/cache#atomic-locks)

**文章变更按事件类型生效，避免全站同时重算。**

| 变更事件 | 相关文章 | 随机推荐 |
| --- | --- | --- |
| 新文章发布 | 索引随已提交写入可用；其他页面到期后有访问、刷新获准且完成时参与排序 | 标记候选池变化，有抽样需求时合并更新；已有批次到期并完成后台刷新后有机会选中 |
| 修改来源文章关键词或分类 | 下次请求立即排除已不相关的旧条目，申请后台重排 | 保留批次，处理与新相关区的重复 |
| 修改候选文章关键词或分类 | 输出时移除已不相关的候选；完整重排遵循周期和后台接纳规则 | 公开资格未变化时继续保留 |
| 修改标题、摘要或封面 | 下次请求使用最新展示内容 | 同左，不因为展示字段改变而换批 |
| 修改 slug、分类路径或固定链接规则 | 下次请求使用当前正式 URL | 同左，不保留旧地址字符串 |
| 下架、转私有、软删除、硬删除 | 下一次状态校验排除，数量不足时少显示 | 排除并补位，补位不足时少显示 |
| 恢复公开 | 与新文章进入候选的规则一致 | 同左 |
| 关闭总开关或某个区块 | 下一次读取已提交配置的请求停止输出 | 同左，关闭状态不执行该区块计算 |
| 应用算法版本升级 | 有访问时限量申请后台重建 | 同左 |

周期约束正常的定期刷新；来源特征修改和失效条目补位可以提前申请，仍受去重和全站限额约束。实际新结果出现时间还包含下一次访问、接纳等待、候选池准备和后台执行时间。因此不承诺新文章在固定 15 分钟或 24 小时内出现在所有旧页面上。“进入候选”表示可以参与选择，不表示一定进入前 N 名。已发送的 HTML 无法收回；下架的承诺边界是变更提交后开始的新输出校验，最终文章入口还需继续执行本身的公开访问检查。

索引更新要覆盖普通模型保存以及批量查询更新。源码中 `ArticleGeoFlowService` 和后台批量操作存在查询式更新；Laravel 官方明确这类操作不会触发普通 `saved`、`updated` 等模型事件，因此不能仅增加一个 Observer 就认为覆盖完成。[Laravel 模型事件说明](https://laravel.com/framework/docs/12.x/eloquent#events)

正常文章写入在同一事务中维护关键词索引，并按文章锁定顺序处理；批量路径分块维护。索引内容以重新读取的当前文章为准。缓存删除和任务派发放在事务提交之后，避免提交前读到旧数据并重新写回缓存。调用方已经持有文章锁时复用原事务。

上线前必须覆盖后台创建与编辑、API、CLI、Worker 生成、AI 优化保存、URL 导入、发布状态流转、恢复和删除的实际落库路径。每日另执行一次分块索引对账，用于修复历史或维护操作产生的差异；这个对账不代替正常写入路径的及时更新。

**并发刷新与故障使用有界处理，正文不等待全站重建。**

页面请求只读取结果、做有界资格校验和提交刷新申请。关键词检索排序、随机换批、候选池重建均由后台处理。同一刷新请求按站点、文章、类型和选择版本去重；后台开始执行时再检查现有结果，已被其他任务完成的工作直接跳过。

全站接纳计数、未完成任务令牌和执行租约存入共享应用数据库的内部运行状态，利用短事务原子维护，避免多个节点分别放行 30 个任务或分别启动一个计算任务。入队失败归还名额，任务完成或最终失败归还名额；恢复流程需要核对队列中的真实任务状态，不能单凭租约到期就把仍在排队的任务当成已结束。暂停队列的验收必须证明推荐任务不会超过 100 个而持续累积。

同一随机批次通过 `(site_key, article_id)` 唯一约束防止重复记录。后台刷新前使用条件更新取得 30 秒生成租约，在事务外完成候选抽样，再核对租约所有者、批次版本和当前选择规则，原子写入结果。租约过期后原持有者的迟到结果不能覆盖新批次。单篇任务最长执行 10 秒，超时进入失败和冷却流程；池构建及历史维护按分块进度接续，每次最多运行 30 秒。

并发请求遇到生成中状态时，使用经过实时公开校验的上一批名单；首次生成且尚无名单时，可暂时隐藏随机区。数据库和本地缓存的不同节点均遵循这一规则。读取失败或池未就绪时，记录内部错误类型及时间，不把技术错误展示给访客。

相关文章到期重算采用同键缓存锁。每条缓存记录保存 `built_at`、`fresh_until` 和 `stale_until`，正常有效期为 R，物理保留到生成后 2R；默认前 1 小时正常复用，后 1 小时仅供等待刷新或短期失败时使用。超过当前 2R 边界时旧结果停止使用，改用同分类临时列表或隐藏。候选文章始终重新校验相关性和公开状态。

随机区等待刷新或短期生成失败时最多使用生成后 2T 的旧批次，默认共 48 小时；超过该边界则隐藏随机区，等待恢复。失败后最早 60 秒再申请，避免每个请求连续重试。两个区块都以少显示、同分类临时列表或隐藏降级，禁止返回已无法确认公开状态的候选。

后台展示索引准备状态、候选池最近构建时间和队列维护错误，不增加新的告警渠道或自动消息发送。维护任务每分钟检查一次少量内部状态，接续需要处理的工作，不每分钟扫描全站文章或所有缓存。候选池根据变化和需求合并重建；历史关键词按 500 篇一块处理，每次任务最长 30 秒并保存进度，继续使用现有队列与调度设施。后台维护显式使用主站范围，不能沿用前一个任务留下的托管站上下文。失败可继续接续，重复处理同一文章保持幂等。

**页面输出和时间戳需要一并核对。**

推荐标题使用真实文章标题，输出标准 `a` 链接与有效 `href`，链接直接指向 `SiteUrlGenerator` 生成的当前正式地址。首屏 HTML 中即可读取链接，不依赖滚动加载、客户端脚本或随机参数。普通站内链接不统一添加 `nofollow`，也不生成 `dofollow` 属性。上述抓取形式依据 Google 的公开说明。[可抓取链接](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)

当前 Nginx 配置在部分站点入口设置了 `no-store`，请求内部转交 PHP 后的最终响应仍需实测。实施时对主站文章的成功 HTML 响应在应用层显式设置 `Cache-Control: no-store`，预览同样禁止缓存。保持既有重定向响应的职责，不把重定向与文章内容响应混为一类。

部署验收要检查实际域名的响应头，确认 CDN 或反向代理没有强制缓存文章 HTML。站点使用自定义整页缓存时，需要同时具备下架清除、设置变更清除和轮换边界失效；首版不接入通用 CDN 清除 API。开启前必须移除冲突的整页缓存规则，否则前述更新时间目标不能成立。

推荐生成只写派生表和缓存，不修改文章正文、发布时间或 `updated_at`。本轮发现 `RecordSiteViewLog` 使用 Eloquent 的 `increment('view_count')`，当前框架实现会追加 `updated_at`，而 sitemap 使用这个时间字段。本次一并把浏览计数改为保留站点作用域的无时间戳更新，并增加回归测试。历史被访问计数推进的更新时间缺少可靠的原始编辑时间，本次不倒推改写这些历史数据。

若以后添加 ETag 或 Last-Modified 条件响应，校验值需要覆盖实际返回的推荐批次与展示变化，避免返回 304 使蜘蛛继续使用旧推荐。首版不新增这套条件缓存。

**模板接入包含数据、挂载点和实际样式三部分。**

系统向文章模板提供 `recommendationBlocks`，每块包含类型、标题和已经筛选好的文章集合；保留 `relatedArticles` 作为旧接口兼容。新机制下，旧接口只映射已开启的相关区；随机数据有独立来源，模板不得再次调用随机查询。

推荐组件使用标准 `partials.article-recommendations` 接口。通过现有主题解析方式优先选择当前模板的组件，再选择系统基础组件。调用位置明确放在正文及标签之后。复用原模板的字号、颜色、内容宽度、标题线、列表或卡片样式；只有存在标准挂载点，基础组件回退才有效。

| 模板类型 | 本期交付 |
| --- | --- |
| 默认主题及项目公开内置主题 | 全部接入统一模块，替换原有页底推荐，并检查侧栏旧推荐是否重复或绕过开关 |
| 本地客户私有模板 | 单独完成当前本地模板适配和预览，文件与素材继续遵守私有交付范围 |
| 以后新生成的模板 | 更新现有模板生成、预览与检查流程，使推荐区随模板一起生成 |
| 外部安装模板已有标准挂载点 | 检查契约版本、依赖和真实文章页渲染，再开放新机制 |
| 外部安装模板缺少标准挂载点 | 显示待适配；制作新模板版本并预览通过后启用，不靠运行时插入脚本猜测布局 |

模板清单增加 `article-recommendations: 1` 能力声明，声明需要与真实接入和测试结果相符。导入导出检查认识这一契约；已有包格式和旧模板仍可用于原功能。用户已经开启新内链时，切换模板必须检查新模板能力；目标模板不支持时，提供“先适配”或“关闭新内链后切换”的明确路径。

对已经支持的主题，模板切换只改变 UI，数据名单沿用当前批次。新模板制作时可以使用现有 AI 模板流程协助设计，实际访客访问和开启普通开关均不调用 AI 生成页面代码。未来任意外部模板的自动修复不属于本期承诺。

随机表只为访问过且开启随机区的文章生成记录，不预生成全站所有文章的随机关系。生成时间超过 90 天的记录可以分块清理；这类记录已超过稳定周期，后续访问自然生成新批次。关键词表及两种推荐结果都可重建，文章业务数据仍保存在原表。

最小实现是缓存一次随机结果并设置 24 小时过期。本方案增加数据库批次记录，用于解决缓存清空、多节点访问和当前批次提前改变的问题；关键词关系表用于避免每次相关查询扫描文章正文或整库关键词文本。新增业务服务共 2 个，第三方依赖、API Key、外部账号、外部服务和必填环境变量均为 0。

单篇刷新必须进入真实的后台队列，不使用请求内同步任务或响应结束后继续占用当前 Web 进程的重建方式。部署沿用已有队列服务，并在本次交付中保证它消费推荐任务。遇到同步队列连接或后台服务不可用时，停用重建派发并在后台显示维护异常，前台按前述规则保留有效结果或降级。后台执行前重新读取当前周期和规则；已经延长周期、关闭区块或已有新结果时，过时任务退出并归还接纳名额。

预计是中等规模改动，涉及超过 8 个文件，主要工作量在全部主题接入、文章写入路径覆盖和并发验证。首版作为一个完整功能迭代交付，后台、查询、更新机制、模板和测试全部完成后再启用。

**实施范围与当前并行工作需要保持清晰。**

主要接入现有 `SiteSettingsController` 与设置页导航、`SiteSettingsBag` 的设置边界、站点 `ArticleController`、`SiteScopedArticleQuery`、`SiteUrlGenerator`、`SiteThemeViewResolver`、模板预览与包检查服务、`ThemeScaffoldWriter`、`RecordSiteViewLog`、路由和调度文件。新增控制器、两个服务、维护任务、派生表迁移、后台视图、主题组件和测试。

首版范围不包含正文关键词自动插入链接、人工指定推荐文章、AI 语义推荐、全站曝光均衡调度、点击归因平台、远程分发站同步和通用 CDN 清缓存集成。无需新增全站关键词编辑系统。

| 周期变更 | 缩短和延长周期均不全站清缓存或集中入队；旧生成时间作为起点；已回收相关名单使用临时列表；延长周期后过时排队任务退出 |
| 内容变更 | 新增、发布、下架、恢复、软硬删除、slug 和分类路径变更；失效 ID 从已缓存结果中剔除 |
| 写入入口 | 后台、API、CLI、批量更新、Worker、AI 优化和导入；事务回滚不发布索引或缓存变更 |
| 并发和故障 | 同页 20 个并发请求只接受一个有效生成结果；多节点、多篇到期页面合计仍只接纳 30 个任务每分钟且计算并发为 1；队列暂停后最多保留 100 个未完成推荐任务；入队失败归还名额；租约超时、迟到任务、首次空批次、同步队列、缓存中断、维护任务暂停和恢复 |
| 候选池按需维护 | 无内容变化且池完整时不重建；内容变化合并处理；没有抽样需求时只保留变化标记；缺块恢复、旧代回收与首次构建不进入文章同步请求 |
| 页面与抓取 | 关闭 JavaScript 后 HTML 中存在正式链接；下架后的新请求不输出旧链接；实际入口 `no-store` 生效 |
| 更新时间 | 访问计数只改变计数；推荐刷新不修改文章 `updated_at`；预览不增加浏览量 |
| 模板 | 全部公开内置模板实际渲染；相关关闭后的侧栏行为；原推荐合并；无图、长标题、空结果、模板切换、外部模板能力检查 |
| 响应式 | 独立测试浏览器检查手机、平板、桌面；不改变用户现有浏览器窗口尺寸 |
| 存量与重建 | 两张派生表空库、历史数据分批回填、回填与正常编辑并发、重复执行、90 天记录清理、版本回滚 |

性能用 1 万和 10 万篇已发布文章验证普通分类、超大分类、常见关键词和大量无关键词四类分布，分别记录冷启动、缓存命中和轮换时的查询数、内存与响应时间。热路径目标是推荐模块新增查询不超过 6 次；抽样和关键词查询不扫描正文、不为每篇访问重新随机排序全库；全站候选池只在维护阶段分块遍历 ID。

在同一测试环境对照关闭模块的基线，目标为正常复用结果的文章请求 p95 增量不超过 30 毫秒；过期请求登记刷新和输出旧结果的增量目标不超过 50 毫秒；单篇后台换批或相关重算的 p95 执行时间目标不超过 200 毫秒，排队等待单独记录。以上是待验证的工程目标；达不到时先检查执行计划、索引和查询范围，修正后再交付，并报告实际结果。候选池首次构建不进入文章请求的同步处理。

额外模拟“一小时内访问 100 篇不同文章”和“短时间抓取 1 万篇冷页面”，比较刷新接纳数、拒绝或暂缓数、峰值计算并发和正文响应时间。后者允许推荐更新延后，必须保持接纳上限和正文可访问，不能为了追上待刷新数量自动提升计算并发或改为前台同步计算。

实现后执行针对性功能与并发测试，再按仓库现有检查要求运行 `vendor/bin/pint --test`、`composer test`、`npm run build`、`npm run test:analytics` 和 `vendor/bin/phpunit -c phpunit.postgresql.xml`。PostgreSQL 检查使用现有专用测试环境，并与 SQLite 功能测试共同覆盖；缺少执行条件时明确记录未验证项，不以文档审查代替测试通过。

**启用和回滚都有明确路径。**

用户确认本文件后，开始代码实现和本地验证。部署迁移只创建派生表及必要索引，历史回填在后台分块执行，避免把全量文章扫描放进长数据库迁移。正常写入的索引维护需要在回填同时生效，回填时锁定当前文章并核对最新字段，避免历史快照覆盖新的编辑结果。

交付前核对全部验收项、主题契约及实际响应头，报告通过项和剩余问题。收到项目约定的“提交”执行指令后，按现有规则完成聚焦提交、PR、检查和合并；生产部署及线上启用仍按用户指定范围执行。

功能级回滚直接关闭内链总开关，停止输出新模块，无需更改文章正文。代码级回滚先关闭新功能和维护任务，再回退应用版本，保留两张派生表及原文章数据；恢复新版本后可重新使用或重建派生数据。旧版本应用会恢复自己的旧推荐行为，不能把代码回滚描述为旧版本也保持新开关关闭。

本文件的确认范围包括：主站两个推荐区、可配置刷新周期、默认 1 小时相关结果与 24 小时持久随机批次、访问触发与后台限量刷新、上述内容变更规则、两张派生表、现有及新生成模板接入、浏览计数时间戳修正和完整验收。确认后按这一范围实施，不提前改动业务功能。
