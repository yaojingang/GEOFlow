## 执行步骤

1. 固定候选并修订执行文件。目标为正式标签 `v3.2.1`，提交 `4bac61bd8c574a1878e3750ae0f59fd22bb28746`，配套 Updater 0.5.0。已有差异报告记录生产迁移 178→180，新增两项；执行前重新对照签名计划与实际迁移记录。补全签名和发布身份验证，修正手册及交接文档，并列明生产入口、SHA 允许清单、覆盖文件与镜像引用的适配方案；未明确范围前不改生产文件。

2. 固定接管目录和数据映射。`/opt/geoflow/shared` 为拟接管实例根目录，先核实它满足 enroll 对配置、storage 和匹配发布版本身份文件的要求。保留 PostgreSQL 16 的实际绝对路径与容器挂载路径，以及现有 Redis `/data` 数据。仅在已审核方案确需改变路径时，于停写后复制完整 Redis 数据并验证，不能重新按“首次挂载”处理。渲染核对所有 Compose 配置及覆盖顺序，保留自动安装、迁移、优化关闭和 loopback 入口限制。

3. 确认静默并创建当次恢复点。核验无临近定时发布和在途任务，开启维护限制，停止调度、排空队列，再停止所有写入进程。停写后才开始记录备份计时，保存同一时间点的 PostgreSQL 完整备份、Redis 完整 `/data`、整个 storage、模板、含原 APP_KEY 的配置、部署脚本、覆盖文件与旧镜像身份。使用绝对路径和统一备份命名，校验归档、清单与恢复所需文件齐全后才进入迁移。若本次继续升级则保持维护；需转移异机副本时，先完成服务器快照并恢复至经验证的运行状态，再传输，避免为传输持续停机。

4. 在真实空闲栈升级 Core。使用签名摘要固定的正式应用和 Web 镜像，按已验证的目标计划执行迁移、图片 readiness、系统知识同步、检索回填、安全审计和缓存预热。Core 的 inspect 与独立 verify 固定签名计划摘要；未受管来源的维护步骤不传虚构序列。预构建镜像需验证前端资源完整；等待应用及依赖健康，再核对产品版本、运行身份和业务数据。后台写入进程及外部入口继续关闭，Core 验收通过后保存 3.2.1 中间恢复点。

5. 独立验证升级前恢复点。在 Core 验收通过后、受管后台启动前，用独立目录、PG16、Redis、旧 app/web 镜像、网络及 loopback 端口恢复升级前恢复点，不共享生产数据、不启后台。逐文件校验 manifest，完整还原数据库、Redis、storage、模板与原 APP_KEY；只在临时目标解除恢复的 Laravel 维护标记，核验管理员认证、业务读取及公共/私有媒体。通过后停止并清理精确标记的临时运行资源，保留恢复点与证据。活栈保持 3.2.1，不为验证备份回滚。

6. 首次接管、蓝绿转换与最终放行。先通过受支持认证读取确认无 active/due 业务任务、待执行发布、AI 工作区及可被调度器恢复的工作，检查旧部署和目标模板涉及的全部队列排空。官方 managed 启动及转换会恢复后台，不能承诺后台始终关闭；无法证明不会触发真实 AI 或发布时停止。校验并安装 Updater 0.5.0，完成 `enroll --instance-id primary --instance-root /opt/geoflow/shared`。启动受管项目之前显式停止旧 geoflow-prod 全部服务，禁止双进程访问数据。按官方交接步骤核对受管配置、配置授权并执行 doctor、update dry-run；维护转换使用该次 Updater 预检摘要，不假定它等于 Core Artisan 计划文件摘要。执行后 verify 通过、签名发布身份对齐、最终入口仍为 127.0.0.1:18080，才恢复外部入口。任一步失败均保留维护并回报，不伪造或手动解除恢复状态。放行后连续观察至少 30 分钟，记录全部阶段耗时、实际停机窗口、异机副本和未完成验收，再交接。

## 验收标准

- 候选运行最终标签配置的 PHP、JavaScript、前端构建、格式及依赖检查，并完成本站 PostgreSQL 16 升级演练。
- 运行镜像、后台版本和 Updater 记录均为 3.2.1，无待执行迁移，`doctor`、`verify` 和业务升级检查通过。
- 等待应用及依赖健康后，验证登录、管理员权限、历史文章、图片、模板、企业知识、系统知识和实时消息。
- 公共图片正常；私有知识媒体认证后可读、匿名访问被拒绝。
- 验证 PDF/PPTX 文本导入、主题兼容、人工发布工单和 AI 可见性相关变更；检查 PHP CLI、`proc_open`、`ffprobe`。扫描件先 OCR。
- 历史保留文章保持原状态，旧质检报告按规则重新检查，普通文章任务显式设置 `need_review`。测试不发送真实渠道内容。
- 未配置模型或未授权真实 AI 调用时，相关验收明确标记待完成，不宣称通过。
- 恢复调度后连续观察至少 30 分钟，无持续队列积压、新失败任务或应用故障，再完成交接。

## 回退与完成条件

- 任一阶段失败，停止并保持维护，保存错误、阶段计时与恢复点位置，向 owner 回报，不自创恢复路径。Core 阶段以升级前完整恢复点作为恢复候选；接管阶段优先采用已验收的 3.2.1 手动部署中间恢复点。涉及回滚活栈或扩大生产配置改动时，须由 owner 确认具体恢复方案后执行。
- 恢复点有效性验证只在独立临时目标进行，活栈正常时不得回滚为 beta.2 做演练。临时验证失败则保留活栈 3.2.1 并停止放行；先查明原因，不能用升级后的新备份替代未通过验证的升级前恢复点。
- 数据库迁移后不单独切回旧镜像，不使用反向迁移代替完整恢复。
- 恢复后先等待健康，再验证登录、数据库、Redis、公共及私有媒体。受管实例保持恢复限制，查询原操作收据并完成逐业务对账；响应不确定时不自动重发。
- 已恢复公众写入后，完整还原须先保存新增数据并明确覆盖范围，不直接覆盖。
- 交接记录包含实际发布身份、检查结果、恢复点、异机副本及未完成验收。保留旧镜像和恢复资料至少 14 天，清理另行安排。
