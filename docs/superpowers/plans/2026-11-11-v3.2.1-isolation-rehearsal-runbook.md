修订：2026-11-11，Asia/Singapore。本轮升级与接管已实际执行，最新收据见[生产执行记录](2026-11-11-v3.2.1-production-execution-result.md)。本版替代原手册全部命令，依据[总计划](2026-11-09-production-v3.2.1-upgrade-and-updater-plan.md)及[现场预检](2026-11-11-v3.2.1-server-preflight-result.md)。

## 目标与边界

直接升级真实空闲栈至 Core 3.2.1，首次 enroll 到 Updater 0.5.0 并真实转换蓝绿布局。升级前恢复点在独立临时 PG16/Redis/app/web 验证，活栈成功后保持 3.2.1。禁止真实 AI、渠道发布、反向迁移，以及两套进程并行访问生产数据。

owner 后续已要求生产操作、提交及推送。实际所需文件范围：

- 新增 `/opt/geoflow/releases/4bac61bd8c574a1878e3750ae0f59fd22bb28746`、`/opt/geoflow/ops/dc-321` 和 staging 下的签名镜像覆盖文件。保留原 dc、release-ref 和覆盖文件作为旧入口，不改它的 SHA 允许清单。
- 完整备份后，生产 `.env.prod` 仅按已审查配置更新签名应用/Web 镜像引用及 `WEB_PORT=127.0.0.1:18080`，并退役会覆盖受管项目名的 COMPOSE_PROJECT_NAME；保留 APP_KEY、凭据和其他业务设置。其 PG16 路径配置继续保留。
- 新增 shared 下正式 `version.json`，以及受管编排要求的 `docker-data/prod/redis`。原 Redis 目录保留，停写停 Redis 后才复制完整数据；不存在“首次挂载到空目录”的原手册前提。
- 官方安装器创建 `/usr/local/sbin/geoflow-updater`、systemd unit、`/var/lib/geoflow-updater`、`/var/backups/geoflow-updater` 和控制 socket。实例文件由 enroll/Updater 生成，不手动改状态或签名 Compose。
- Caddy 仅切换既有 GeoFlow 标记区块的维护入口；恢复时保留其他应用区块及并发变更。其他服务不重启。

## 部署适配与 Core inspect

新增 dc-321 使用目标源码 compose、原 ops/compose.override.yml、staging/compose.signed-images.yml，显式 `-p geoflow-prod`。最后一层为所有应用服务固定签名镜像，避免旧 env 中的镜像引用覆盖目标。

先渲染配置，核对 PG16、shared/postgres、shared/redis、shared/storage、loopback 18080 及自动安装/迁移/优化关闭，然后执行：

```bash
/opt/geoflow/ops/dc-321 config --quiet
/opt/geoflow/ops/dc-321 run --rm --no-deps \
  -e AUTO_MIGRATE=false -e AUTO_INSTALL_ONCE=false -e AUTO_OPTIMIZE=false \
  -e AUTO_FIX_STORAGE_PERMISSIONS=false \
  app php artisan geoflow:upgrade --phase=inspect --json
```

预期 version=3.2.1、计划摘要匹配，仅两项 pending。Artisan inspect 不返回 source_sequence。本站 beta 未受管且没有签名发布序列，Core 采用既有维护脚本模式逐项执行计划步骤，再独立 verify；不套用官方来源 3，不编造序列或 apply journal。

## 维护与一致恢复点

先限制入口、`artisan down`、停止 scheduler/web，确认所有已知队列 pending/delayed/reserved 均为 0，再优雅停止所有应用、Reverb 和 Worker。确认无在途写入后才制作备份。

本次维护备份脚本位于 staging/maintain-backup.py。执行前读全脚本并核对其原容器 ID、旧镜像与退出恢复逻辑。它以绝对路径生成 `/var/backups/geoflow/pre-321-时间戳`，包含：

- PostgreSQL custom dump、roles.sql，dump 列表可读取。
- 停止 Redis 后保存的完整 redis-data.tar.gz，含多段 AOF 与 manifest，另留 RDB 和 keyspace 记录。
- storage.tar.gz、旧源码/模板归档、ops 归档、production.env、release-ref、覆盖文件、原 Caddy 配置和旧容器/镜像身份。
- manifest.json，逐文件校验；目录 0700、文件 0600。

备份失败且尚未迁移时，按已验证的原容器 ID 启动原服务，等待应用和依赖健康后恢复入口；不得依赖会报缺 init 的 compose start。备份成功后保留维护态，仅 PG/Redis 运行以供迁移。若需要异机副本，生产恢复至健康状态后再传输。

## Core 维护升级与中间恢复点

对照签名计划 steps 逐项执行。所有一次性容器使用 `run --rm --no-deps`，自动安装/迁移/优化关闭；迁移时显式设置排空确认，绝不启动旧 Worker：

```bash
/opt/geoflow/ops/dc-321 run --rm --no-deps \
  -e AUTO_MIGRATE=false -e AUTO_INSTALL_ONCE=false -e AUTO_OPTIMIZE=false \
  -e AUTO_FIX_STORAGE_PERMISSIONS=false \
  -e GEOFLOW_SECURITY_FRESH_INSTALL_CONFIRMED=false \
  -e GEOFLOW_SECURITY_UPGRADE_DRAIN_CONFIRMED=true \
  app php artisan migrate --force --no-interaction
```

然后按签名步骤顺序，通过同样的一次性容器执行 managed-images readiness、system-knowledge sync --media、retrieval backfill 及 --verify、安全审计和 config/route/view cache。每项成功后才继续；执行 `geoflow:upgrade --phase=verify --json`，产品版本从 version.json/升级报告读取，不用 artisan --version。

保持后台和外部入口关闭，启动 app/reverb/web 并等待健康，只做管理员与业务读取验收。保存 3.2.1 手动部署中间恢复点，包含同一时间点 DB/Redis/storage/config 与新镜像身份。

## 独立临时目标验证升级前恢复点

使用独立目录、内部网络、旧 app/web 镜像 ID 和 PG16/Redis8，只启动 PG、Redis、app、web。不共享任何生产数据挂载，不启 Worker、scheduler 或真实外部调用。

1. 逐文件验证 manifest；在临时 PG16 完整 pg_restore，退出 0。
2. 解包完整 Redis 数据归档后启动，核对 PONG、AOF 状态和 keyspace，区分自然过期键。
3. 备份包含 storage/framework/down。只在临时恢复实例执行 artisan up，不删除生产维护标记。storage 归档解到实例根目录，只产生一层 storage；验证原 APP_KEY、模板和文件哈希。使用 tarfile data_filter 时，路径验证后恢复目录模式。
4. 通过临时 Web 验证管理员认证读取、历史文章、公共图片与私有知识媒体。匿名私有访问应拒绝，认证读取与媒体哈希匹配；不得重置生产管理员密码绕过认证。
5. 停止并删除精确标记的临时容器/网络，保留升级前恢复点与证据，不删除生产数据或旧镜像。

临时验证失败时，活栈保留 3.2.1、入口继续维护，回报原因；不得把升级后的新备份作为升级前恢复点已通过的证据。

## 首次 enroll 与真实蓝绿转换

进入本节前，先完成前节的独立恢复验收。官方 managed Compose 启动和 Updater 转换会解除 Laravel 维护并启动后台，不能承诺后台一直停止到转换后。仅在认证业务读取和完整队列排空证明无可执行业务后进入；外层维护限制保留。若要求继续维持业务 hold 而当前版本无受支持解除流程，应停止，不手动改恢复状态。

安装已验证的本地 Updater 包，确认 version=0.5.0、protocol=5。Core 验收后写入匹配的正式 version.json；保留原 APP_KEY 和 PG16 路径；按签名编排要求，在停 Redis 后复制 shared/redis 全目录至 shared/docker-data/prod/redis，验证文件及 keyspace，保留原目录。

```bash
sudo geoflow-updater enroll --instance-id primary --instance-root /opt/geoflow/shared
```

保留 enroll 输出于受限证据目录，审查生成配置。旧 geoflow-prod 所有服务包括 PG/Redis 必须停止后，才启动 enroll 输出的 managed Compose，绝不并行访问数据。两个 env 文件都需提供；渲染后再次确认端口仅 127.0.0.1:18080。旧 COMPOSE_PROJECT_NAME 必须退役，使签名 flat/infra/slot 名称生效；旧手动包装入口用显式 -p，并固定自身 WEB_PORT=18080，避免双重 host 插值。授权 URI 仅保存到受保护文件，不打印到聊天或 Git。

签名 flat 桥接 init 会全量修改 storage 权限。先只启动 PG/Redis，再单独运行 init 并等退出 0；确认没有应用/后台运行后，恢复事先捕获的 uid/gid/mode 并校验业务文件哈希，再用 --no-deps 启动明确的应用服务集合。不要用普通 up 重跑 init 依赖。生成蓝绿布局的 init 已关闭该权限扫描。

等待 managed 应用及依赖健康，再执行 doctor 和 update dry-run。按真实返回结构读取其 plan_sha256；这是 Updater 预检摘要，不是上面的 Artisan 计划文件 SHA。核对 source/target sequence=4、version=3.2.1、maintenance、layout_change=true 及零 pending，再执行带该摘要和 allow-maintenance 的 update。保存操作编号、恢复点与最终收据，不自动重发不确定请求。

转换后 verify 通过，核对 blue-green 布局、活动 slot、签名镜像和 loopback 入口。外层维护限制继续保留。独立恢复已在受管后台启动前通过，转换和业务验收也通过后才放行。

## 计时、放行与停止规则

本次新计时字段依实际顺序为 T0_maintenance_start、T1_drained、T2_recovery_point、T3_core_up、T4_identity、T5_recovery_verified、T6_enrolled、T7_updater，另记 external_opened_at 和观察结束时间。它们替代旧版不符合停写顺序的 T0–T7 定义。

签名漂移、备份不完整、非空目标目录来源不明、迁移失败、版本/镜像/挂载不符、enroll/doctor/dry-run/update/verify 失败均停止，保留维护和受限日志。涉及回滚活栈时先回报具体恢复方案，不自动反向迁移、手动改 Updater 状态或重复不确定请求。

后台由经前置验收的官方受管事务恢复；全部门槛通过后恢复外部入口，观察至少 30 分钟，确认无持续积压、新失败任务或应用故障。报告实际发布身份、恢复点、计时、异机副本、验收和待办。仅通过功能分支提交本次文档及必要脚本，不提交凭据或业务数据。

本站恢复 HTTP 的 18091 loopback 探针已验证不可达，不能据此移除 internal 隔离。实际验收使用容器已检查的内部 bridge IP，通过仅操作员可达的临时 Caddy 前缀完成；验收后前缀、容器及内部网络全部撤除。初次失败探针与后续成功验证分开留存。
