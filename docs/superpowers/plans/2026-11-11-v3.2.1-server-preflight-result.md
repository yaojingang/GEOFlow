## 阻止继续执行的事实

1. Redis 已持久化。`docker inspect geoflow-prod-redis-1` 显示 `/opt/geoflow/shared/redis:/data` bind mount。`/opt/geoflow/ops/compose.override.yml` 已定义该挂载，目标也已有 RDB/AOF 数据。手册 §2 的“首次挂载、目标应为空”前提不成立。不得另挂空目录或覆盖原数据。
2. 生产 Compose 入口不同。`/opt/geoflow/shared/docker-compose.prod.yml` 不存在。真正入口 `/opt/geoflow/ops/dc production` 使用 releases 下固定 SHA 的 compose，再叠加 ops/compose.override.yml。该脚本拒绝未列入允许清单的 release-ref，直接切到 v3.2.1 SHA 不能工作。升级前必须明确新的命令入口和覆盖文件顺序，不能丢掉 PG16、数据挂载、自动迁移关闭和 loopback 端口限制。
3. 备份段不能照抄。§1.1 先 cd 恢复点再相对读取 storage、.env.prod、compose，会指向不存在的文件；pg_dump 只是注释。备份与恢复段对 `.env.prod`、`.env.prod.bak` 命名不一致。§0.5 要求暂停写入后记 T0，§1.1/§1.2 的命令顺序却先备份后停写。必须先修正路径、命名与一致性顺序。
4. Updater 接管缺少 enroll。v0.5.0 官方 README 与 CLI 源码要求先运行 `enroll --instance-id primary --instance-root ROOT`，再操作 primary。仅安装二进制后直接 doctor/update 不会登记现有站点。站点 root、版本身份文件、数据库路径、旧项目停机与 managed Compose 切换均需明确；不能让两套进程同时接触业务数据。
5. 临时恢复 compose 不具备验收条件。§5.1 写 PG18，与本站 PG16 不符，且 PG18 数据挂载路径需另核；app 镜像为 PHP-FPM，现网 app 只暴露 9000，映射 18091:80 不能提供 HTTP，必须加入 web 服务。Redis 没注入 REDIS_PASSWORD；storage.tar.gz 含 storage/ 顶层，再解到 ./storage 会嵌套；`interval: 10s; timeout: 5s; retries: 10` 不是三个 YAML 字段。恢复命令和清理命令还漏了自定义 compose 的 -f。临时端口应显式绑定 loopback。

另有验证口径问题：手册把 `artisan --version` 当作产品版本，把本地 build 结果要求为 GHCR 发布 digest，并期待 inspect 返回 source_sequence。现场旧版 inspect 不含 source_sequence；来源序列必须继续核对目标版本代码与来源身份，不能猜值。178→180 是本站新增两项迁移，28 项是官方 3.1.0 来源示例。
