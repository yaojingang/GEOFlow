# GEOFlow 与 Updater 联合部署升级方案

日期：2026-09-08。状态：已批准设计，代码实现见 [操作指引](../../blue-green-deployment-usage.md)；生产部署与发布尚未执行。目标：统一首次安装、自动升级动作、兼容版本在线切换与故障恢复。

## 1. 现状与判断

GEOFlow 已有首次空库安装入口 `deploy-scripts/geoflow-docker-deploy.sh`，使用 `docker-compose.prod.yml`，包含环境准备、镜像构建、初始化、迁移和健康检查。已有数据的升级走停机排空协议。

`geoflow-updater` 已具备宿主机更新执行器：TUF 验签、镜像摘要固定、预检、备份、迁移、激活、恢复服务、验证及中断恢复。Laravel 通过 Unix socket 发起受限操作。后续改造继续保持 updater 为唯一更新执行者。

实现基线：GEOFlow `6383e956a28fa86a27454ef615d10d93a48914dd`，updater `724bf4ffd21101757b3e26f5dd70ac6cb3445b40`。当前操作接口与已完成验证见操作指引和验证记录；本方案保留设计目标及验收要求。

| 已核对位置 | 当前行为 | 改造要求 |
| --- | --- | --- |
| GEOFlow `deploy-scripts/geoflow-docker-deploy.sh` 的 `deploy_stack` | 进入维护模式，停止应用服务，执行 init，再启动 | 保留首次安装语义；新的统一入口识别首次安装与受管更新 |
| updater `internal/update/engine.go` | 固定执行 quiesce、backup、migrate、activate、resume、verify | 增加经过签名兼容性检查的在线更新策略 |
| updater `internal/deployment/service.go` 的 `quiesce` | 停止 queue、knowledge-queue、scheduler、reverb、web、app、redis | 与当前 GEOFlow 的全部服务保持一致；在线路径保持基础设施运行 |
| updater `assets/docker-compose.managed.yml` | 固定容器名、单套应用和入口 | 拆分稳定基础设施与可并存的应用槽位 |
| GEOFlow `docker-compose.prod.yml` | 还包含 ai-quality-queue、ai-quality-backfill-queue、ai-optimization-queue | 补入受管模板、doctor、排空及验收；以绑定发布的服务清单为准 |
| updater `Migrate` | 一次性容器执行 `artisan migrate --force` | 编排迁移后的业务回填、官方知识同步和发布检查 |
| updater `internal/operation/manager.go` | 根据已有阶段判断中断恢复 | 按策略分别恢复；在线策略禁止隐式整库还原 |

以上服务差异是 updater 远端模板与 GEOFlow 当前工作区的对比，不能据此判定某台线上机器的实际运行状态。

## 2. 可用性边界

推荐采用两种升级策略，由同一个 updater 根据签名发布清单和实例状态选择。

| 策略 | 适用范围 | 网站行为 | 自动失败处理 |
| --- | --- | --- | --- |
| `online` | 旧、新代码能共同读写当前数据；待执行迁移和队列格式均通过兼容性声明及测试 | 网站持续服务，新请求切到新槽位，旧请求完成后回收旧槽位 | 保留当前数据，切回兼容的旧应用 |
| `maintenance` | 旧版安全升级、破坏性结构变更、不兼容任务格式、基础设施升级、首次受管结构转换 | 提前显示需要维护窗口；获准后排空，完成升级再开放流量 | 开放写入前可以恢复完整检查点；开放后按单独恢复流程处理 |

现有 `docs/deployment/DEPLOYMENT.md` 3.1 节明确禁止已有数据实例执行 migration-first 或滚动升级。对应迁移 `2026_07_17_000403_add_managed_path_hash_to_images_table.php` 会调用 `SecurityUpgradeMigrationGate::assertReady()`，并在回填后把路径哈希改为非空。直接让旧进程继续写入会违反这个安全前提。

实施时保留这条历史迁移门禁。只有完成这次排空升级、并符合签名清单允许来源的实例才能进入后续在线升级；未声明兼容性的迁移默认要求维护窗口。不得为实现蓝绿效果，给在线运行中的迁移注入排空确认变量。

“不停机”首版验收范围为普通 HTTP、API、登录会话和支持时限内的在途请求。后台任务允许排空造成处理延迟。Reverb 连接采用客户端重连和状态补拉，AI 流式响应应在切换前继续完成。无法在时限内排空时保留旧槽位并报告清理待完成，不强行中断后宣称无损升级。

单机 CPU、内存、磁盘、Docker、数据库或稳定入口本身故障仍会影响服务。在线升级所需容量应覆盖新旧应用并存峰值；以预检和压测值作为准入依据。

## 3. 部署结构与所有权

```text
管理员命令 / GEOFlow 更新中心
              |
        geoflow-updater
       /      |       \
签名发布清单  操作日志  稳定入口路由
                         |
                  +------+------+
                  |             |
              blue 应用      green 应用
                  |             |
                  +------+------+
                         |
                PostgreSQL / Redis
                    共享业务文件
```

新增一个稳定入口容器，使用现有 Nginx 技术栈；TLS、域名和外部端口保持由当前反向代理方案管理。入口通过内部网络访问活动槽位的 web，槽位自身的 web 与 app 成对部署，避免静态资源和 PHP 版本混用。

updater 管理三类 Compose 项目：固定基础设施、blue、green。PostgreSQL 和 Redis 仅运行一份，业务更新不重建它们。受管模板移除应用固定容器名，槽位名和镜像摘要写入 updater 自有状态；禁止两个 PostgreSQL 实例挂同一数据目录。

每个槽位保留独立应用网络，web 只连接本槽位的 PHP 服务；连接共享网络的服务使用带槽位的唯一别名，避免两个 `app` 或 `web` 的 DNS 别名混用。数据库网络、入口网络的连接范围分别限定。

持久化布局由 updater 管理：`instances/primary/infra/` 保存基础设施与入口配置，`slots/blue/`、`slots/green/` 保存各自 Compose、release.env 和版本信息，`deployment-state.json` 保存活动槽位、上一版本、策略、操作 ID 与阶段。状态文件采用原子替换，重要边界写盘后才执行下一动作。

入口切换先生成并验证新配置，再原子替换并平滑 reload。记录旧入口 worker 的进程身份，等待旧 worker 和旧应用请求排空；只收到 reload 成功不能判定排空完成。切换后通过入口新建连接核实实际返回的 release ID，确保控制状态与真实路由一致。[Nginx 官方说明](https://nginx.org/en/docs/control.html)确认 reload 会创建新 worker，并让旧 worker 处理完已有连接。

Kamal Proxy 已提供健康检查后切流并等待旧流量排空的机制，可作为独立代理备选。本方案先复用现有 Nginx，减少新增分发依赖；若实际验证证明难以可靠观测排空，再改用这个成熟组件。[Kamal Proxy](https://github.com/basecamp/kamal-proxy)

## 4. 在线更新事务

1. **解析和预检。** 验证签名、发布序号、最低 updater 协议、允许来源版本及镜像摘要。确认当前实例健康、没有其他更新操作、空闲槽位可用、资源足够。枚举所有待执行迁移及其哈希，逐项核对签名清单。
2. **准备候选版本。** 拉取目标镜像，生成空闲槽位配置。显式关闭容器自动迁移和安装填充；预检不启动 scheduler 或消费业务队列。
3. **创建在线备份。** PostgreSQL 使用一致性数据库快照导出；记录发布状态与文件清单。现有完整备份依赖停止 Redis、冻结业务文件，应继续归入维护操作。在线备份必须标注一致性范围，不能冒充数据库、Redis、文件跨系统同一时刻的恢复点。
4. **执行兼容升级动作。** 在新镜像的一次性容器内执行允许的迁移和升级步骤。针对实际待执行迁移加锁并设定锁等待、语句执行及整体超时。失败时停止本次更新；保留旧应用服务，已完成的向前兼容迁移保留，日志记录部分进度。
5. **启动并检查候选应用。** 启动候选 web、app、Reverb，验证 Laravel、数据库、Redis、必要表结构和资源读写。通过带真实 Host 的内网请求验证后台登录页、前台、静态资源及版本身份；此时不开放公共流量。
6. **切换入口。** 写入切换意图，验证并 reload 入口配置，读取真实路由结果，持久化活动槽位。切换和落盘之间崩溃时，恢复逻辑根据入口实际版本完成或撤销切换。
7. **交接后台服务。** 旧 scheduler 停止产生新任务并等待子进程结束；旧 worker 停止领取新任务，完成在途任务后退出。确认旧代停止后再启动新代 worker 与 scheduler。新旧 HTTP 共存及交接期间的队列 payload 必须双向可读，不满足时选择维护策略。
8. **观察和保留回切点。** 默认连续探测 120 秒，并覆盖登录、业务读写、后台任务和 WebSocket 重连。任一强制检查失败，确认旧版仍兼容当前数据后回切应用。保留上一版镜像、配置与静态资源，禁止清理仍被连接或发布状态引用的槽位。

缓存按用途隔离：共享登录会话、业务锁、队列和限流状态；编译视图、配置缓存、路由缓存按槽位保存。禁止在线路径运行会清空共享缓存的 `optimize:clear`；Laravel 官方明确它会清理默认缓存驱动的所有 key。候选容器使用细分的配置、路由和视图缓存命令。[Laravel 部署文档](https://laravel.com/framework/docs/12.x/deployment)

共享 `APP_KEY`、会话 cookie 设置和会话后端。上传、主题、生成内容继续使用共享业务存储；编译视图从共享目录中分离。前端构建资源按内容哈希保留当前及上一版本，避免旧页面延后请求资源时出现 404。清理条件需包含保留期和引用检查。

两个 Reverb 实例共存时必须启用 `REVERB_SCALING_ENABLED=true`，使用同一个 Redis 广播总线，并验证旧连接能收到新应用产生的事件。该配置在初次拓扑交接中完成。客户端断线后从业务状态补拉；Redis 发布订阅不能代替事件持久化。未通过跨实例事件与重连检查的发布不进入在线策略。[Laravel Reverb 扩容文档](https://laravel.com/framework/docs/12.x/reverb#scaling)

## 5. 自动迁移与升级动作

增加随应用版本维护的 `deployment/upgrade-plan.json`，由 TUF 作为发布目标签名，绑定目标镜像摘要和源提交。该清单使用固定步骤类型与参数校验，updater 不执行清单中任意 shell 字符串。

| 契约字段 | 规则 |
| --- | --- |
| `schema_version` | 新契约版本，旧 updater 通过最低协议版本明确拒绝无法理解的清单 |
| `allowed_sources` | 允许直接升级的已签名发布序号；跨度过大时先要求升级到明确的中间版本 |
| `strategy` | `online` 或 `maintenance`；在线准入同时要求实例检查通过 |
| `migrations` | 文件名、SHA-256、在线兼容结论；实际待执行集合必须被清单完整覆盖 |
| `compatibility` | 旧版对目标结构、任务 payload、共享缓存和文件格式的兼容范围 |
| `steps` | 稳定步骤 ID、前置条件、执行阶段、超时、重试规则和验收规则 |
| `rollback` | 能否在当前数据上回切旧应用；需要完整恢复时必须明确数据边界 |

GEOFlow 提供统一命令 `geoflow:upgrade`，包含 `--phase=inspect|apply|verify` 与结构化 JSON 输出，内部调用既有服务或命令。宿主机负责升级锁、进程状态与操作日志，应用负责业务数据的前置条件和完成判断。命令处于新镜像中，不能在旧应用执行新版本升级逻辑。

| 动作 | 来源 | 执行与验收 |
| --- | --- | --- |
| 数据库迁移 | `artisan migrate --force --no-interaction` | 单实例排他执行；完成后复查实际迁移集合，不能只看退出码 |
| 三层召回回填 | `geoflow:backfill-ai-quality-retrieval` | 仅对适用源版本执行；回填后检查 tasks、tasks_deferred、checks、checks_staled、sources、knowledge_bases、readiness_projections、atomic_fact_counts 全部归零 |
| 受管图片 readiness | `geoflow:managed-images:readiness` | 按来源及数据状态执行；remaining、terminal、registry_failed 都为零 |
| 安全审计 | `geoflow:security-audit --json` | 复用当前 JSON 输出和失败语义；需复核的 finding 保留明确阻塞原因 |
| 官方系统知识同步 | `geoflow:sync-system-knowledge --key=ai_workspace_manual --media` | 保留管理员编辑，验证知识资源哈希及写入状态；异步处理的验收单独记录 |
| 配置、路由、视图缓存 | Laravel 对应缓存命令 | 在候选槽位执行，验证资源和权限，不清空共享业务状态 |

给现有只有表格输出的回填命令补结构化结果，避免依赖终端文本。每个步骤记录 operation ID、步骤 ID、计划哈希、目标版本、状态和完成证据；可重入步骤重复调用返回已完成，长回填保存游标。不对任务投递、文件写入或外部动作宣称通用 exactly-once，需要使用现有幂等键和恢复检查。

数据库在线准入同时审查读写兼容与锁行为。新增字段也可能获取强锁，不能仅根据“添加字段”放行。初始锁等待上限建议为 5 秒，语句上限由签名步骤设置；大表索引和回填拆成可恢复步骤，避免把长事务塞入切流窗口。[PostgreSQL ALTER TABLE 文档](https://www.postgresql.org/docs/current/sql-altertable.html)

## 6. 回滚与中断恢复

| 失败位置 | 处理方式 |
| --- | --- |
| 验签、下载、预检、候选启动 | 当前活动版本继续服务，清理范围限定于本操作创建的候选资源 |
| 在线兼容迁移中途失败 | 保留旧应用及已完成的兼容迁移，记录失败步骤，允许诊断后重试 |
| 在线切流后健康失败 | 重建或启动上一槽位，检查其对当前数据仍兼容，切回入口；保留升级期间的新写入 |
| 在线旧请求排空超时 | 保留旧槽位，标记清理待完成，禁止复用该槽位；不会通过强杀制造成功状态 |
| 维护模式、开放流量前失败 | 停止所有写入方，验证完整检查点，再恢复数据库、Redis、业务文件和配置 |
| 已开放写入后需要整库恢复 | 单独显示恢复点时间和潜在数据损失范围，使用已有恢复授权；不能作为普通在线失败处理 |
| updater 崩溃或主机重启 | 对照持久化策略、阶段、活动槽位和真实入口状态恢复；优先维持已健康的路由 |

现有 `Engine` 会在 resume、verify 失败时调用整套恢复。新实现需要把“对外开放流量”定义成明确的恢复边界，健康检查尽量前移到内部入口；在线路径和对应启动恢复分支不得调用现有整库恢复方法。

## 7. 首次安装和后台统一入口

保留 `geoflow-docker-deploy.sh` 的兼容入口，新增 `scripts/geoflow-deploy.sh` 作为面向使用者的统一入口。它负责调用已安装的 updater；环境检测、核心变更和操作记录由 updater 执行。

- **新安装：** 验证下载包的来源、摘要和签名，安装 updater，再由新增 `install --instance primary --root /opt/geoflow --url https://geo.example` 初始化受管布局、空库、环境文件和首个 blue 槽位。随机生成管理员初始密码，不输出固定密码。发现已有数据、未知目录内容或已有密钥时停止首次安装路径。
- **已受管实例：** 复用 `update --instance primary`。增加 `--dry-run --json` 输出版本、策略、升级动作、资源要求和阻塞项；执行时绑定计划哈希，防止预检与执行之间目标变化。
- **已有非受管实例：** 保留 `enroll`，核对安装版本与签名发布身份。先备份并排空，进行一次维护窗口的拓扑交接；旧、新基础设施不可同时占用数据目录。完成基线交接后才允许在线更新。
- **维护升级：** 新的自动化调用默认要求操作中明确允许维护；后台提交对应计划及授权码，避免“在线更新”失败后静默转为停机操作。已安装旧 CLI 的既有维护行为保持兼容，新增选项通过协议版本区分。

更新中心继续使用既有 socket、实例 token、分操作验证码和防重放机制。展示目标版本、是否影响访问、迁移及回填步骤、当前阶段、失败原因和可用回切目标。网站“回切应用”与“恢复数据”使用不同操作类型和文案，日志明确记录恢复范围。

## 8. 可独立交付的实施顺序

本次完整实现会涉及两个仓库、超过 8 个文件，并增加一个常驻入口容器。应按三个可独立使用的交付单元推进，避免一次混入所有风险。

### A. 补齐受管升级动作

保持现有维护升级模式，补齐当前应用版本的服务模板、doctor、排空清单和升级动作。引入签名升级清单与应用升级命令，补齐结构化回填输出和幂等检查，修正开放流量后的恢复边界。该阶段完成后，已有维护升级可自动执行完整动作。

阶段 A 的新升级动作契约使用最低 updater 协议 3，保持读取现有协议 2 发布的能力。新发布清单不能交由无法理解升级动作的旧 updater 执行。

GEOFlow 主要位置：`app/Console/Commands/`、新增 `app/Services/Deployment/`、`deployment/upgrade-plan.json`、`tests/Feature/`、`tests/Unit/`、部署文档。updater 主要位置：`internal/managed/`、`internal/tufclient/`、`internal/tufrepo/`、`internal/deployment/`、`internal/doctor/`、`internal/update/`、`internal/operation/`、受管 Compose 与发布工作流。

### B. 增加在线蓝绿策略

引入基础设施与槽位模板、入口配置、策略选择、请求排空、后台交接、在线备份标识和应用回切。在线发布要求最低 updater 协议升级到 4，避免只有阶段 A 能力的 updater 误接在线更新；旧协议清单按维护模式解释，未知字段或不兼容协议明确拒绝。新协议发布前先完成同一候选包的双架构演练。协议编号在实际实施时先核对远端最新值，已被占用时递增分配。

updater 新增 `internal/traffic/` 与 `internal/deployment/bluegreen.go`，扩展实例状态、更新状态机和崩溃恢复测试；`assets/` 新增基础设施、槽位和入口模板。GEOFlow 补候选版本 readiness、视图隔离、带版本的资源保留、worker 排空证据和兼容性测试。

本阶段可通过宿主机 CLI 完成在线升级，阶段 C 尚未交付时也可独立使用。

### C. 统一首次安装与操作界面

实现签名受管首次安装、统一脚本、预检计划展示和后台在线策略入口。更新 `SystemUpdaterBridgeService`、`SystemUpdaterOperationController`、现有更新中心页面及本地化；保留历史运行和备份只读访问。同步用户文档、包内文件清单和升级指引。

最小交付是阶段 A，能够满足“自动执行迁移升级动作”；达到日常升级保持网站访问需要阶段 B。阶段 C 完成一条使用入口的产品体验。

## 9. 验收和发布条件

开发验证使用隔离工作区与临时 PostgreSQL、Redis、Compose 项目。主工作区已有其他任务修改，不能以混合工作区测试通过作为本次改动的独立证据。

| 场景 | 通过条件 |
| --- | --- |
| 全新安装 | 空库迁移、管理员初始化、blue 活动、所有必需服务和 readiness 通过；重跑不覆盖数据或密钥 |
| 无迁移在线更新 | 持续 HTTP 请求没有因切换产生的连接失败或 5xx，版本切换可验证 |
| 兼容迁移在线更新 | 老版持续读写与迁移并发，新版启动后继续通过；同一升级步骤重入不会重复业务副作用 |
| 历史安全迁移或未声明迁移 | 在线预检明确拒绝，未设置排空确认，未执行 schema 变更 |
| 锁等待超时或迁移失败 | 旧网站继续服务，部分升级结果被准确记录，无整库自动恢复 |
| 候选、切流、后台交接失败 | 故障注入后按阶段保持旧版或回切，升级期间写入的数据仍存在 |
| 全部后台队列 | 普通、知识、AI 质检、回填和优化任务均覆盖；迁移前排空证明完整，交接无丢失与重复外部副作用 |
| 登录、上传、静态资源 | 原会话持续有效；切换前后上传可读；旧页面加载旧资源成功 |
| Reverb 和 AI 流式响应 | 在途流完成或按约定重连与补拉；排空超时不会被记作无损完成 |
| updater 崩溃 | 在每个持久化边界前后终止进程；重启后活动槽位与真实路由一致，禁止同时启动两个 scheduler |
| 完整恢复边界 | 开放写入前恢复所有检查点范围；开放写入后恢复需要单独操作授权 |
| 发布身份 | amd64、arm64 使用同一批准候选的源提交、TUF 目标及镜像摘要，禁止重新构建后沿用旧验收证据 |

updater 执行 `go test -race ./...`、`go vet ./...` 和所有新增 Compose 模板的 `config --quiet`，扩展当前 `phase-c-rehearsal` 覆盖在线策略。GEOFlow 执行新增升级命令和兼容性测试、现有 updater 桥接和镜像配置测试，以及 `.github/workflows/ci.yml` 要求的相关检查。压测结果保存请求数、错误数、升级前后新增记录、任务副作用次数和排空证据。

开发与本地测试无需生产凭据。候选镜像发布沿用 GHCR、GitHub Actions 和现有 TUF 签名环境；签名私钥继续留在受保护环境。真实主机部署另外绑定具体主机、域名、实例路径和已验证的恢复点。本设计未连接生产主机，也未执行数据库迁移、发布或容器切换。
