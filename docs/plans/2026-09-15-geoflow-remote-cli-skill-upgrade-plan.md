# GEOFlow 远程 CLI 管理与 Skill 升级方案（最终版）

日期：2026-09-15
版本：v1.1，已完成一轮方案 review 与修订
状态：已确认，按批次实施中；本文保留方案核查时的历史基线
对象：GEOFlow Core、独立 CLI、`geoflow` skill、第一方托管站与 GEOFlow Agent 目标站

当前实现范围见 [远程管理预览版覆盖说明](../api/remote-management-preview.md)。本文中的目标和验收项用于后续实施，不能作为已完成功能或已发布版本的声明。

## 建议与预期效果

**建议迭代 GEOFlow skill，并同步升级系统 API、CLI 分发方式和主题运行机制。** 用户安装 skill 与 CLI、连接一次目标实例后，可以在 Codex 或具备终端能力的 AI 平台中完成后台管理，通过远程草稿持续修改前台，预览后发布，并随时回到历史版本。

建议采用三个配套交付：

- **GEOFlow Core**：提供覆盖后台业务的管理 API、权限与能力发现、远程主题草稿、版本发布和回滚。
- **GEOFlow CLI**：从当前仓库内客户端演进为独立安装的客户端，统一连接、命令、文件增量、异步进度和结果回读。
- **`geoflow` skill**：以远程实例操作为默认入口，按任务加载说明，复用 CLI 的确定性行为；保留源码开发与旧版迁移入口。

用户可以直接说：

> 连接我的 GEOFlow，看看哪些文章待审核。把网站首页改成更简洁的资讯布局，先给我看预览。确认后发布，保留上一版。

AI 在后台完成实例识别、权限检查、数据读取、远程草稿修改、预览和发布。日常模板迭代无需人工下载、解压、上传和安装 ZIP；文件内容与图片仍需通过网络传输，由 CLI 按需处理。已有模板包继续服务跨实例交付和备份。

### 本次建议确认的五项决定

| 决定 | 推荐选项 | 原因 |
| --- | --- | --- |
| 总体架构 | 扩展现有 API v1 + PHP CLI + 单一 `geoflow` skill | 复用已有鉴权、业务规则与测试，维护一套业务逻辑 |
| 远程操作入口 | CLI 使用 HTTPS 访问目标实例 | 用户终端无需 GEOFlow 源码、数据库、Docker 或 SSH |
| 模板修改方式 | 服务端草稿、增量写入、不可变版本、独立发布 | 支持持续迭代、并发保护和回滚 |
| 上线次序 | 先连接与基础管理，再主站模板，然后补齐管理与多站点 | 每一批都可单独使用，尽早实现主要使用场景 |
| 发布权限 | 延续账号权限；原生 Blade 修改按代码部署权限管理 | 保留现有模板能力，同时明确服务器执行边界 |

### 本轮 review 的结论

**保留 Core + 独立 CLI + skill 的方向，补齐实施顺序、权限签发、远程编辑上下文和故障恢复契约。** 原稿存在以下会影响实际交付的问题，已在本版对应章节修订：

| 问题 | 修订结果 |
| --- | --- |
| 新权限缺少首次签发入口，部分基础设施放在后续批次 | A 交付请求 scope 的登录、自身令牌撤销、操作收据和查询；B 才开放统一外观写入，签名安装随首个发布包交付 |
| 能读文件，但 AI 无从得知模板变量、模块和路由规则 | 增加按站点返回的主题契约、可编辑范围、依赖与配置 schema；记录每轮优化的基线和结果 |
| 恢复整份历史配置可能覆盖后续管理员修改 | 代码版本与站点配置版本分开；回滚按实际改动字段生成差异，逐字段检查并发变化 |
| 写请求响应丢失后可能没有 operation ID；换 token 后旧幂等记录不能直接重放 | 请求发出前持久化客户端请求 ID；新增跨 token 的同账号操作查询与独立去重，保留旧幂等行为 |
| 草稿快照、发布准备与垃圾回收之间存在引用竞态 | 增加容量预留、准备状态、引用保护、清理锁与崩溃恢复；明确多副本接入条件 |
| 原生代码权限和站点隔离的关系不够明确 | 将 Blade 权限定义为实例级代码信任；配置预览复用已信任代码，普通站点权限不等于 PHP 隔离 |
| “所有管理”遗漏了一些后台子流程 | 补文章编辑助手、微信 HTML 导出、人工发布账号/人设、模板复刻、敏感词等；增加可核对的覆盖口径 |
| A+B 的范围及原估算容易被理解为全部管理已完成 | 明确 A+B 为现有运营能力加主站模板闭环；C+D 达成完整覆盖，重新给出按批次的人日区间 |

本轮再次核对 GitHub，最新正式版和 main 提交与初稿一致。方案 review 完成不代表新增接口、跨平台安装或线上发布已经验证通过。

## 现有 Skill 为什么需要升级

现有 skill 能指导开发和部分远程操作，但入口与系统能力已经不匹配。

| 现有设计 | 当前影响 | 本次调整 |
| --- | --- | --- |
| 先要求 workspace，再运行发现与 preflight | 只有远程地址的用户难以直接开始 | 优先发现已安装 CLI 和实例配置；仅源码任务要求工作区 |
| CLI 固定按 0.2.0 能力说明 | 新后台功能不能自然进入命令体系 | 每次读取目标能力和操作 schema，版本号作为兼容辅助 |
| CLI/API 缺项转向管理页面、Cookie 和 CSRF 表单 | 仍依赖后台页面结构，维护成本高 | 新版使用正式管理 API；旧版缺项明确提示升级 |
| 主题发现主要扫描 `resources/views/theme` | 覆盖不到持久化安装主题和远程实例 | 服务端统一返回内置、安装、草稿和已发布版本 |
| 模板修改创建本地 fork，再替换目录 | 要求源码和共享文件系统，远程使用不便 | 服务端创建草稿；CLI 读取所需文件并提交增量 |
| 渠道实时能力检查依赖本地 PHP、artisan 和应用环境 | 普通 AI 终端必须准备完整项目 | 由连接的 GEOFlow 后台代理渠道检查，CLI 只取结果 |
| 静态地图与包规则停留在旧流程 | 容易漏掉 URL 管控、安装主题、托管站与新权限 | 保留业务解释，操作清单由系统契约生成 |
| 全局和项目内入口可能同时存在 | 安装路径和版本容易混淆 | 仓库作为唯一源码，发布包统一生成平台适配文件 |

另有两项需要明确承接的历史决定：

1. 旧在线 Theme Editor 已被移除，测试要求旧入口返回 404，且不能执行或修改线上模板。新能力采用独立的远程草稿与发布协议，保留旧入口关闭和源码目录保护测试。
2. 2026-09-08 主题包方案将“版本更新、在线修改、公共 API/CLI”排除在当时首版之外。本次用户提出的新需求扩展该范围，并继续复用已完成的持久化与包校验能力。

依据：[现有 skill](../../.agents/skills/geoflow/SKILL.md)、[模板编辑流程](../../.agents/skills/geoflow/references/theme-edit-workflow.md)、[旧编辑器关闭测试](../../tests/Feature/AdminSiteThemeEditorTest.php)、[模板包设计](../superpowers/plans/2026-09-08-site-theme-import-export-design.md)。

## “所有管理”如何定义和验收

覆盖目标为：**连接实例已启用、当前管理员有权执行的全部 GEOFlow 后台业务操作，都有可发现、可调用、可验证的 CLI 入口。** 同一后台业务的列表页、编辑页、表单提交可以合并为一个资源操作族，纯页面导航不需要复制成 API。

所有新命令、接口、表名和版本号在后文均为拟议设计，当前 CLI 0.2.0 尚不支持。

### 能力边界

- 每个业务操作都必须覆盖 schema、权限、正常响应、失败响应、影响范围和结果回读。API 返回成功但远端分发尚未完成时，只能报告“已受理”。
- “人工发布工单管理”包含工单与回执；微信、媒体平台等第三方的真实发布仍遵守现有连接与人工/浏览器执行能力。
- GEOFlow 的远程管理凭据管理 GEOFlow 自身。SSH、操作系统、数据库直连、任意 shell 和任意 Artisan 执行不作为远程 API 暴露。
- 已接管实例可经现有 Updater 完成运维动作。首次安装、服务器损坏或 Core 完全不可达时，仍需宿主机 Updater CLI；这是独立的恢复通道。
- Codex 和其他平台需具备终端执行及目标网络访问能力。纯聊天平台无法直接运行 CLI，可消费方案和说明；不承诺仅粘贴 SKILL.md 即具备执行能力。

在 A 建立 `management-coverage.json`：逐项记录 Admin 路由、控制器动作、业务 operation ID、API、CLI、权限、功能开关、状态、批次和验证证据。353 条 Admin 路由作为当前盘点基线，不直接等同于 353 项业务功能。后台中的运行开关、任务健康/worker 状态、标题就绪检查、特殊提示词及模型绑定等子流程也逐项登记。

覆盖统计分为两项：① 路由分类率，A 起要求全部有归属；② 业务操作交付率，按去重后的业务 operation 计算，C+D 完成后要求全部交付。纯导航、已有操作的表单展示和失效兼容跳转可以附依据排除；有数据或副作用的动作不能以“页面”排除。权限不足和功能关闭属于运行时状态，不能从产品覆盖分母中删掉。注册条目需有实际 handler、权限验证和结果证据，只有空命令不算交付。CI 按各批次清单检查，不让尚未实施的后续批次阻塞 A/B 的独立合并。

## 用户操作体验

### 连接一次，后续按实例继续

安装包提供 `geoflow` 命令。用户提供实例公开根地址，通过隐藏密码输入、受保护的标准输入或已有 token 连接。浏览器设备授权可作为便利选项；纯 CLI 登录持续可用。

拟议入口：`geoflow login --base-url https://geoflow.example.com --profile production`。这里的域名为示例。

连接成功只返回实例名称、账号、角色、有效 scope、版本、到期时间和配置位置，凭据安全保存。AI 不需要让用户把密码贴到对话里。

后续执行 `geoflow --profile production doctor`，检查身份、API 契约、所需能力以及相关服务是否可用。多实例使用显式 profile；当前目录中的未知配置不能自动把既有 token 发往另一地址。

| 用户意图 | CLI 操作 | 结果 |
| --- | --- | --- |
| 查看线上网站当前状态 | `site get primary`、`theme list --site primary` | 当前站点、主题版本、配置版本与页面样本 |
| 为这次优化创建草稿 | `theme draft create --site primary --from active` | 服务端草稿 ID、基线版本和可编辑资源 |
| 了解页面能够使用什么 | `theme contract --workspace WORKSPACE_ID` | 模板数据、路由、模块、资源 helper 和配置 schema |
| 找到需要改的文件 | `theme file list`、`theme file read`、`theme file search` | 仅返回所需路径、内容或片段，以及文件摘要 |
| 修改布局、样式、模块 | `theme file patch`、`theme file write`、`theme config patch` | 整批校验并写入草稿，返回新草稿版本 |
| 检查并查看效果 | `theme check`、`theme preview` | 检查结果、受控预览链接、页面覆盖情况 |
| 发布已确认版本 | `theme publish plan`、`theme publish apply` | 影响清单、发布记录、线上版本和回读结果 |
| 下一轮继续优化 | 从当前 active 再创建草稿 | 可跨对话恢复，无需重新下载完整模板 |
| 恢复上一版 | `theme rollback plan`、`theme rollback apply` | 恢复模板及本次版本管理的外观配置，保留业务内容 |

表中主题子命令均显式携带目标草稿或版本 ID；简写仅用于说明操作顺序，实际参数由 `--help` 和 schema 提供。

用户已明确授权的检查、草稿修改和范围内执行持续推进。只要求预览时，流程停在预览；明确要求发布时，按已授权范围提交发布动作。风险确认内容始终绑定具体对象和变更，已获得的有效授权不重复询问。

“持续优化”首先指可续接、可比较、可回滚的多轮迭代。定时诊断或自动发布须另有明确的频率、站点、额度和发布授权，本次不创建任何后台定时任务。

每轮在草稿与操作收据中保存目标、起始版本、变更摘要、检查/截图引用和发布结果。布局、可用性、SEO 结构及素材体积可做前后比较；访问量、转化和 AI 可见性的变化通过 `analytics`/`visibility` 按相同站点、时区、区间和过滤口径读取。主题检查不能据此宣称流量或 GEO 排名提升。缺少浏览器或统计数据时，报告实际缺失的证据，下一会话可以继续补验。

## 系统架构与契约

```text
Codex / 具备终端能力的 AI 平台
              |
       geoflow skill（任务流程）
              |
       独立 GEOFlow CLI（确定性客户端）
              | HTTPS + 绑定实例的 token
              v
GEOFlow API v1：能力发现、鉴权、参数校验、操作审计
              |
       共享业务服务与资源策略
       /           |             \
 内容/知识/管理   主题草稿与版本   分发 / Updater 适配器
       |           |             |
  数据库与队列  持久化文件+站点绑定  Agent 目标站 / 宿主机工具
```

系统继续使用 Laravel、PHP、已有数据库、Redis、队列和持久化 storage。核心管理与主题修改不新增常驻代理服务；已有渠道适配器和 Updater 继续承担它们的专门职责。

### API 路径与操作注册

- 保留当前 `/api/v1/tasks`、`materials`、`articles` 等接口及旧客户端行为。
- 新增 `/api/v1/capabilities` 与 `/api/v1/auth/session`，提供能力发现和当前身份。
- 新管理接口位于 `/api/v1/management/`，按 sites、themes、analytics、distribution、knowledge、system 等业务域组织。
- 以服务端 `ManagementOperationRegistry` 为操作元数据来源，关联 operation ID、路由、请求/响应 schema、scope、风险类型、幂等策略和异步结果类型。原 CLI `OperationRegistry` 转为消费该契约的兼容层，避免两处手工维护操作清单。
- 生成 OpenAPI 3.1 文档和 CLI 内置操作目录；真实路由、注册表、生成结果通过契约测试核对。请求校验保持在各业务 Request/验证器中，并与 schema 测试对齐。
- CLI 提供易读的业务子命令，以及 `geoflow api OPERATION_ID --input -` 通用入口。通用入口只调用已注册的相对路径，执行相同权限与确认逻辑；远端元数据不包含可执行脚本。

通用入口使低频操作及时可用，常用操作继续提供专门命令。返回 schema 发生不兼容变化时升级契约版本；新增可选字段和操作维持 API v1 的兼容性。

### 握手内容

能力响应包括 `instance_id`、Core/CLI 协议版本、构建提交、当前身份、有效权限、可用操作、站点类型、各主题契约版本、文件限额、异步查询方式和功能未启用的原因。

实例 ID 持久化保存，客户端绑定公开根 URL、部署前缀和实例 ID。备份克隆为新实例时重新生成身份；检测到目标身份变化先重新确认连接。服务端按实际部署和当前管理员返回能力，不能只根据版本号或本地 skill 说明推断。

能力和会话自查允许任意有效 token 查询自身信息，不要求先获得新的管理 scope。能力接口返回 404 时，再用已存在的认证或只读旧接口确认 GEOFlow 响应格式和部署前缀，才能判定旧协议；仅凭代理返回的 404 不判定版本。401、403 和代理错误分别处理。能力缓存绑定实例、账号和契约摘要，权限变化后刷新；写操作最终仍由服务端实时授权。

操作 schema 采用固定、受限的声明格式；远端不能指定外部 `$ref`、任意 URL、执行脚本或本地文件路径。CLI 只接受其已支持的契约版本和传输类型；不支持的扩展返回能力缺失，提示兼容 CLI 版本。

### 共享业务规则

新 API 控制器调用已有服务；仍留在 Admin 控制器内的业务校验和数据变更，按业务域提取成共享服务后，由 Web 与 API 同时调用。禁止直接调用页面控制器、内部重放后台 HTTP 表单或复制另一套状态机。

执行身份从 `ApiAuthContext` 解析当前有效 Admin，复用 `BaseApiController::executionAdmin()` 的现有检查，显式传给业务服务。使用 `auth('admin')` 的页面逻辑需要迁移到共同策略，API 不建立或伪造 Web 登录会话。统计接口也复用查询服务，并在结果中返回时区、区间边界、过滤条件和生成时间。

复用 `ApiAuthContext`、`ApiTokenService`、`IdempotencyService` 和 `ApiResponse`，保留 `success/data/error/meta` 响应格式。新增统一操作收据，包含请求 ID、对象 ID、基线/结果版本、异步 operation ID 和可回读地址。

### 权限与敏感动作

权限计算取账号当前角色、业务资源策略、token scope 与实例能力的共同允许范围。账号停用、角色或模型共享范围变化，在请求及异步任务执行前重新校验。

新增主题 scope 分为 `themes:read`、`themes:write`、`themes:code`、`themes:publish`；站点、模型、分发、账号、更新等域按 read/write/execute 或专有动作划分。原生 Blade 和任意脚本内容只能由具备代码权限的超级管理员操作。普通配置权限只能修改经过 schema 约束的字段。

旧登录默认的九项 CLI scope 保持原集合。新管理 scope 要求令牌显式列出，旧 `*` 不自动获得本轮新增权限；旧 API 对已有 scope 的匹配规则保持兼容。`themes:code` 还需工作区代码授权，默认 30 分钟有效。权限与授权到期后可以重新授权继续同一草稿。

**首次连接与授权在 A/B 就形成完整流程：**

- A 扩展 `POST /api/v1/auth/login`，允许可选 `requested_scopes`；不传时仍签发旧九项。CLI 用 `login --scopes ...` 显式请求，服务端以本次密码认证的账号策略核验全部 scope；未知或不允许的权限明确报错，不静默缩减后声称授权成功。CLI 保存前核对实际返回集合。
- A 提供 `GET auth/session` 和 `POST auth/logout`；退出撤销当前令牌并清除本地秘密。断网时可清除本地凭据，但必须明确远端撤销尚未完成。其他管理员和批量令牌管理在 C 完成。
- B 提供 `POST management/theme-workspaces/{id}/code-authorizations`。要求有效超级管理员、显式代码 scope 与当前密码再认证，授权绑定拥有者、草稿、实例及有效期；每次代码变更、动态检查和发布记录确切内容摘要。最终 apply 仍绑定已审核的版本与计划。
- 新增主题计划默认 15 分钟有效、一次消费；工作区代码授权与普通业务报告分别验证。服务端确认的是账号授权和具体变更，用户在对话中的发布意图由 skill 按当前任务保留和执行，不能由一个本地 `--yes` 代替。

令牌签发不能扩大调用者权限，也不能通过指定另一管理员越权。登录、撤销、当前会话读取、到期和多实例切换均需有独立契约测试。

URL 变更、渠道删除、密钥查看、数据恢复等动作沿用业务自己的报告、口令、当前密码或授权码要求。CLI 的 `--yes` 仅处理本地交互，服务端继续核验报告和授权。授权凭据绑定操作者、目标、动作、基线、变更摘要、有效期；密码、token 和敏感授权码不进入审计详情或标准输出。

密钥查看、渠道包和线索导出使用独立权限与现有业务确认，通过受保护的文件输出完成；默认不返回原文到对话或普通 JSON。CLI `--output-file` 默认创建权限 0600 的新文件，拒绝符号链接及隐式覆盖；JSON 只返回本地文件位置、大小和摘要。需要同时提供业务 JSON 与秘密时，使用单份受保护输入或独立输入文件，不能让两个选项竞争同一个 stdin。渠道密钥和包导出继续持有渠道操作租约。

### 幂等、并发与异步

- 新建、发布和外部副作用使用幂等键；相同键不同内容返回冲突。重试保留原键，不能把网络超时自动转为新的发布。
- 更新携带资源版本或 `If-Match`。基线过期返回 409，缺少要求的前置条件返回 428；CLI 重新读取差异后再处理。
- 长操作返回 202 与 operation ID。`operation get/wait/cancel` 将现有作业类型映射为统一状态，内部仍使用原任务记录和队列。仅实际支持取消的类型暴露 cancel；取消请求不撤销已发生的远端副作用，最终状态须回读确认。
- CLI `wait` 使用有界等待和退避；读取类请求可有限重试，外部动作先查询收据。完成状态采用 `succeeded/failed/cancelled`；`needs_reconciliation` 表示暂停自动推进、仍需对账，允许授权对账后继续或结束，不能当成成功或自动重试。
- 高风险本地变更与必要审计/收据在同一事务提交；远端调用先登记操作意图，再记录结果。现有尽力记录的后台日志不能单独承担发布收据。

A 即提供 `GET management/operations/{id}`、`GET management/operations/lookup?client_request_id=...` 与等待所需字段，并为既有任务入队接入首个真实作业适配器；B 接入主题，C 扩展其他业务类型。CLI 发出支持新契约的写请求前，先持久化实例、账号、operation 名、`client_request_id`、幂等键及非秘密摘要，通过 `X-Client-Request-Id` 传递请求身份；获取响应后补记 operation ID。旧接口仅在协商出该能力且携带新头部时启用收据封装，旧客户端保持原行为。即使整个 202 响应丢失，也能按客户端请求 ID 查结果。lookup 静态路由须先于 `{id}` 路由匹配。

现有 `IdempotencyService` 的指纹包含 token ID。保留该兼容行为，并为新管理操作增加 `(instance, actor, client_request_id)` 唯一约束和包含目标、动作、基线、内容的业务摘要。重新登录后，当前有效账号可在资源权限范围内查询原操作；同 ID 不同摘要返回冲突，同 ID 已执行返回收据，不再执行副作用。密码和令牌不持久化为重试正文，必要秘密重新输入。尚在执行或状态未知时，先查询/对账，不能换新 ID 重发。

新操作的入队意图随数据库事务保存，由可重试调度器投递，worker 领取时原子检查操作状态与执行租约；补偿扫描恢复提交后未投递的记录。外部结果不确定时沿用领域对账规则。基础收据保留至少 90 天，运行中和待对账记录不清理；主题发布历史及必要去重索引随引用继续保留。客户端保存未完成请求摘要，完成后按保留期清理，短期内容缓存与续接记录分开。

Laravel 的 Sanctum token abilities 与资源策略可作为基础；继续适配项目现有 `ApiAuthContext`，避免套用只认识 Web 登录会话的权限检查。[Sanctum 文档](https://laravel.com/docs/12.x/sanctum)、[Authorization 文档](https://laravel.com/docs/12.x/authorization)。

## 远程主题迭代的系统适配

这部分决定能否省掉模板包往返。当前系统已经支持可信原生 Blade 模板的安装，但尚无可远程编辑的草稿、可持续更新的版本和站点发布记录。

### 服务端保存草稿与版本

沿用 `storage/app/private/geoflow-site-themes` 作为主题持久化根目录，增加 `workspaces` 与 `revisions`。现有 installed、uploads、exports 继续有效。

| 对象 | 拟议存储 | 核心字段与规则 |
| --- | --- | --- |
| 远程草稿 | `site_theme_workspaces` + `workspaces/{id}` | 站点、拥有者、来源主题/版本、基线摘要、草稿版本号、状态、检查报告；仅草稿可修改 |
| 不可变主题版本 | `site_theme_revisions` + `revisions/{id}` | 逻辑主题 ID、来源、完整文件清单、内容摘要、配置 schema/默认值、依赖及契约、创建者；就绪后只读 |
| 站点当前绑定 | `site_theme_bindings` | 唯一 `site_key`、当前 revision、外观配置快照/版本、绑定乐观锁版本、旧主题映射；主站与托管站各自绑定 |
| 发布历史 | `site_theme_releases` | from/to revision、配置前后值及实际变更项、操作者、检查摘要、收据与回读状态；纯配置修改及回滚也产生记录 |
| 操作收据 | `management_operations` | 业务类型、原任务引用、幂等身份、计划摘要、授权有效期、状态和结果；保存高风险计划及消费状态 |

以上为新增数据设计，共五类表；业务领域已有 job/run 表继续使用。主题文件保存在文件系统，数据库保存引用、状态与审计，不把整套文件塞入数据库。

草稿默认保留 7 天无活动期限；每个站点的已发布版本至少保留最近 10 个且不少于 30 天。仍被站点、有效预览或发布任务引用的版本禁止清理。磁盘达到限额时阻止新写入并提供清理报告，不自动删除仍受保护的版本。这些值是建议默认值，区别于现有主题包 60 分钟临时令牌期限。

草稿起始配置和 patch 与文件版本关联保存；主题 revision 只冻结代码、素材及其契约，当前站点外观配置单独计版本。一次代码修改不会自动获得回写全部站点配置的权利。

默认每管理员最多 10 个活动草稿，主题受管存储预算为 2 GiB，且写入后至少保留 1 GiB 磁盘可用空间；实例可调整，doctor 返回实际值。这些是新增容量策略，不代表当前线上配置。容量统计包含 staging、未引用候选、草稿快照和历史版本；复制前预留额度，失败后释放。无引用的旧草稿快照仅保留最近一次恢复点，防止每次 patch 累积整套副本。

revision 使用 `preparing/ready/deleting` 状态和操作租约。清理器先锁定记录、重新检查站点/预览/计划引用及租约，再标记 deleting；发布只接受 ready 且能取得引用保护的版本。文件删除在事务外执行，可重复清理。崩溃后按收据核对 staging、准备状态与数据库指针；未经确认的残留不能被激活。大文件复制不占用数据库长事务。

### 统一发现三种来源

1. **内置主题**：从当前运行版本创建服务端快照，生成受管主题身份；后续修改写入草稿。
2. **已安装主题包**：保留原安装收据和来源记录，从其文件创建草稿；原始安装不被覆盖。
3. **已发布的受管主题**：从指定 revision 创建新草稿，支持两个操作者分别迭代。

默认站点的 `site.*` 回退页面也须能成为草稿来源。建立明确的页面依赖清单，补齐用户要改的页面；无法复制或映射的依赖在检查阶段阻止发布。

复刻任务“发布”当前只生成包。升级后保留包导出动作，新增直接生成远程草稿的动作，由同一预览与发布流程接管，避免让“包已生成”继续被误解为“网站已上线”。

### 远程模板契约

新增 `GET management/theme-workspaces/{id}/contract`，由当前 Core、站点类型和草稿共同生成，CLI 映射为 `theme contract`。返回：

- 页面类型与入口文件、可用模板变量及其类型、空态约定和已发布样本引用。
- 当前站点的 URL/分页规则、素材 helper、允许的组件和跨主题依赖。
- 首页模块、外观参数、广告和表单引用的 schema；各项能否编辑及所需权限。
- 固定的 Core 构建、渲染契约版本和依赖摘要，以及校验器能够验证的项目。

仅暴露公开渲染所需的数据结构与授权范围内的配置，排除数据库凭据、管理员对象和任意应用内部文件。此契约随系统代码测试更新，不能让 AI 根据模板注释猜变量，或要求用户提供整个源码目录。

### 文件接口与增量协议

| 拟议 API | 作用 |
| --- | --- |
| `GET management/sites`、`GET management/themes` | 发现站点、主题来源及当前版本 |
| `POST management/theme-workspaces` | 按站点和基线创建草稿 |
| `GET management/theme-workspaces/{id}` | 查询草稿及版本号 |
| `GET management/theme-workspaces/{id}/contract` | 获取站点渲染与编辑契约 |
| `POST management/theme-workspaces/{id}/code-authorizations` | 为可信代码修改和候选渲染建立短期授权 |
| `GET management/theme-workspaces/{id}/files` | 分页列文件，返回逻辑路径、类型、大小和 SHA-256 |
| `GET management/theme-workspaces/{id}/file` | 用逻辑路径读取文件或有限范围 |
| `GET management/theme-workspaces/{id}/search` | 有界全文搜索，限制命中数和上下文 |
| `POST management/theme-workspaces/{id}/changes` | 原子应用一批新增、修改、删除及配置 patch |
| `POST management/theme-workspaces/{id}/file-contents` | 流式暂存大文本内容，返回 content ID，供 changes 引用；按文件类型核验代码权限 |
| `POST management/theme-workspaces/{id}/assets` | 上传单个待引用资源，返回资源 ID；通过 changes 一起纳入草稿版本 |
| `POST management/theme-workspaces/{id}/checks` | 校验文件、依赖、渲染与页面契约 |
| `POST management/theme-workspaces/{id}/preview-sessions` | 建立只读、短期预览会话 |
| `POST management/theme-workspaces/{id}/publish-plans` | 固定草稿版本与目标基线，生成发布计划 |
| `POST management/theme-plans/{id}/apply` | 校验授权和基线后执行发布或回滚计划 |
| `GET management/sites/{site}/theme-releases` | 查询发布记录 |
| `POST management/sites/{site}/theme-rollback-plans` | 撤销指定发布，或选择历史代码版本生成恢复计划；使用同一 apply 契约 |

所有地址均相对 `/api/v1/`，为新增接口设计。

`changes` 必须携带 expected workspace version；每个修改和删除携带原文件摘要，新增要求目标不存在。使用无模糊匹配的补丁或完整内容替换，整批成功或整批失败。冲突返回当前摘要和差异范围，不提供强制覆盖别人新修改的默认选项。

草稿每一批修改先写独占 staging，完整校验后保存为新的草稿文件版本，再以数据库版本比较切换草稿指针。预览固定读取指针指向的版本，避免读到半批文件；失败残留只回收未引用的版本。

配置修改只允许 schema 声明的外观字段，包括首页模块、风格参数和本次选择纳入版本的展示配置；颜色、链接、资源和富文本按字段规范校验，配置通道不接受任意脚本、事件属性或 Blade 表达式。站点域名、后台路径、账号、密钥、分析脚本权限和文章固定链接保持各自专门的管理契约。

每个配置项携带基线版本/摘要；模块数组作为一个完整配置项校验，禁止对已变化的数组索引做模糊合并。初期采用保守冲突提示，CLI 展示新旧差异后重新生成 patch。新图片上传先形成私有待引用对象，校验后由 changes 原子接入，未引用资源按临时期限回收。

继续沿用现有单文件 5 MiB、500 个文件、总量 25 MiB 的默认上限。新增文本读取每次最多 256 KiB，patch 请求最多 1 MiB；大型文本使用有界分段读取，通过 file-contents 流式暂存，再在 changes 中用 content ID 完成替换。二进制资源通过 assets 流式传输，单独校验大小、MIME 与摘要。两类暂存对象均绑定草稿与操作者、写入后不可变，默认 60 分钟内接入草稿；接入时重新核验摘要、权限和总容量，不因持有 ID 就能跨草稿使用。

现有 CLI 的 JSON 响应上限为 5 MiB，不能把一个 5 MiB 文件再完整编码进 JSON 响应。新增传输实现保持 JSON 上限，对文件使用独立流式限额；无需提高所有 API 请求的限制。

路径限定在草稿声明的逻辑文件树内，统一拒绝目录穿越、绝对路径、符号链接、特殊文件、重复与大小写冲突。CLI 不接受远端返回的本地命令、任意目标路径或任意下载 URL。

### 模板执行权限需要单独说明

原生 Blade 可以在服务器执行 PHP。当前已安装模板预览调用真实控制器并渲染模板，iframe 和 CSP 约束浏览器侧行为，无法隔离模板在服务器侧对数据库、文件或网络的访问。现有 `ThemeComplianceGuard` 的正则检查也不能充当 PHP 安全沙箱。

因此分为两种编辑权限：

- **外观配置编辑**：只修改系统声明的模块、样式参数和受控资源引用，沿用对应业务权限。
- **可信模板代码编辑**：允许修改 Blade、CSS、JS，需超级管理员及显式 `themes:code` 授权，按代码部署操作记录。工作区与授权关联，短期有效；动态预览本身也检查代码权限。

原生 Blade 的权限边界是整个 GEOFlow 应用运行身份。API 的 site_key 校验能约束管理请求，无法保证获准执行的任意 PHP 只访问一个站点。因此代码权限仅授予实例级可信维护者；托管站认证验证系统契约和可见性行为，不构成恶意代码隔离。已发布且已信任的代码摘要可由配置编辑者复用；未修改代码的配置预览不额外要求代码部署权限。账号授权到期阻止后续编辑、候选渲染与发布，不使已发布网站随令牌到期下线。

推荐首版保留可信原生模板能力。未知来源模板只做源码和依赖检查，未取得代码信任授权时禁止动态渲染。若未来要求普通租户提交任意不可信代码，需要另建无生产凭据的独立渲染环境；该目标会增加常驻服务与运维成本，不包含在当前推荐实现中。

### 预览真实页面，隔离业务副作用

预览使用当前实例的已发布内容，覆盖首页、搜索、分类、文章、关于、归档总览和月度归档。无内容页面显示真实空态，不创建演示文章。

预览 context 固定 site、workspace revision 和外观配置，处理结束后恢复视图查找器与缓存上下文。系统预览流程不得修改 `active_theme`、生产配置、阅读计数、统计、线索、发布映射或分发记录。Laravel 长驻进程连续处理两个站点时也要验证隔离。此约束覆盖框架受控流程；自定义原生代码仍受前述代码部署信任边界约束。

CLI 请求预览会话后获得默认 15 分钟有效、可撤销的只读链接。它只授权指定站点、草稿版本、外观版本和允许页面，不能调用管理 API。每次渲染核验创建者当前状态；含新代码的候选还核验代码授权。页面使用 noindex、private/no-store、no-referrer 和 CSP sandbox，允许展示所需脚本时仍不允许 same-origin、顶层导航、弹窗和表单提交；预览入口不借助管理员 Cookie 获取额外权限。访问日志遮蔽预览凭据，资源链接受同一会话约束。过期或草稿删除后，链接失效。视觉检查记录被沙箱限制的交互，不能把这些交互宣称为线上功能已验证。

默认生成检查 JSON 和预览链接。具备浏览器的环境可通过可选 `theme check --visual` 调用独立浏览器检查器，输出截图与桌面/移动端检查报告；检查器使用项目已有 Node.js 技术栈的可选组件。缺少浏览器时明确显示“未执行视觉验证”，仍可完成 CLI 管理和预览生成。共享浏览器维持用户当前窗口尺寸，固定尺寸检查使用独立上下文。

### 发布采用完整版本与一次绑定切换

发布计划固定以下信息：目标站点、当前主题及配置版本、待发布 revision、变化文件、影响页面、实际配置 patch、检查结果与回滚目标。检查报告还绑定 Core 构建、渲染契约和依赖摘要。草稿变化、站点版本变化或依赖变化都会使计划失效；Core 维护/更新期间拒绝新 apply，更新结束后重新检查并生成计划。

执行顺序：

1. 在私有 staging 完成整个 revision，核对文件、依赖和落盘结果，再以同文件系统原子重命名保存为只读版本，登记 ready 和计划引用。目标存储必须满足持久化要求；仅文件可见不等于断电后仍有保证。
2. 在短事务内锁定站点绑定及相关引用，重新检查操作者、基线、维护状态、发布计划和幂等记录。
3. 一次提交站点 revision 绑定、相关外观配置投影、发布历史及收据。事务中不进行远程请求或大文件复制。
4. 对线上页面执行回读，记录当前 revision、资源状态和失败原因。

文件系统和数据库不具有共同事务。文件完成但数据库提交失败时留下未引用 revision，由清理器回收；数据库只引用已经就绪的完整版本。缓存按 revision 分区，避免必须依靠全量清缓存才能正确运行。

站点请求在入口固定一次 revision 和外观快照，模板与资源始终来自同一版本。后台现有主题选择、首页模块、预设导入、风格和广告等所有外观写入入口统一调用站点外观服务；`SiteSettingsBag` 等读取方使用同一请求快照，禁止继续直接覆盖受管字段。既有设置表保留兼容投影，绑定快照作为受管站点外观的读取依据；配置保存形成可追踪的配置版本。

发布后回读失败时，收据标记明确异常，并分别返回“绑定已生效”和“回读是否通过”。只有发布计划事先允许失败自动回切，且当前 revision 与外观版本均仍是本次结果时才自动恢复；否则保留诊断并由授权的回滚命令处理，防止覆盖期间另一位管理员的新发布或配置修改。自动回切后也要回读并记录失败，不能只凭切换请求返回成功。

### 解决现有资源路径和主题依赖

现有主题可能硬编码 `theme.{id}`、`/themes/{id}` 或引用另一内置主题。复制目录后全局替换 ID 容易破坏模板和脚本，不能作为版本管理的基础。

采用以下适配：

- 逻辑主题 ID 与物理 revision 分离。原始主题 namespace 作为依赖信息保存，解析器在请求内解析到选定 revision，并清理路径缓存。
- 新版本公共素材使用包含 revision 的不可变地址，例如 `/theme-assets/{revision}/{path}`。仅公开已发布版本清单中的允许素材，Blade 和私有工作区文件不可下载。
- 草稿素材走预览授权入口。草稿不能因为知道 revision ID 就公开访问。
- 新模板使用统一主题素材 helper；旧模板的静态引用在建草稿时生成可审查的迁移差异，动态引用须明确声明和适配。
- 无法解析的跨主题引用、运行依赖或资源地址阻止发布。需要的自带文件进入版本快照，系统公共视图依赖声明对应契约范围。
- Nginx、HostedAssetController、主题视图解析器和部署保留目录同步适配。内置 `/themes/` 资源仍服务旧主题，受管 revision 使用独立地址。

这样可以避免旧 Nginx 静态文件优先级遮蔽新 CSS，也避免浏览器缓存拿到上一版资源。

### 回滚与应用升级

回滚明确分为两种模式，CLI 与计划结果必须写明：

- **撤销一次发布**：指定 release ID，切回该次发布前的代码，仅恢复该次实际修改的外观项。代码绑定必须仍指向该次结果；各待恢复项的当前摘要也必须等于该次写入值。期间被再次修改的项返回冲突，无关外观项保留。例如一次发布只改颜色，后来后台调整广告，撤销颜色发布必须保留新广告。
- **采用历史代码版本**：显式指定 revision，默认沿用当前站点外观；若同时恢复历史配置，必须选择历史 release 和恢复项，先形成新的差异计划。计划固定当前版本，应用时再检查，不能整份覆盖历史快照。

两种模式都产生新 release，先检查目标代码与当前配置/资源的兼容性。文章、分类、线索、URL 规则和业务发布记录维持各自状态；表单、分类或模块依赖已删除时，报告缺项并阻止不兼容恢复。发布收据引用的回滚目标在保留期内受到清理保护。

Core 更新前预检所有当前绑定版本与目标 Core 的契约兼容性。升级计划同时固定主题绑定/配置版本，准备至切换期间阻止冲突写入。备份包含新增表、绑定与持久化文件，并在维护状态下完成一致性快照；恢复演练检查所有数据库引用都有对应文件，不能只备份数据库。

B 的正式支持范围是单应用实例、持久化本地 POSIX 文件系统。多副本部署在 E 完成专项验收后启用：共享主题目录、锁与重命名语义检查、共享版本状态以及完整副本清单均为前提。新增副本须注册部署标识并上报构建/契约/存储就绪状态，接流量前探针验证；未知拓扑或缺失副本证据时关闭主题发布能力。滚动升级期间旧副本退出流量后才允许新契约激活，不能仅由一个副本的 doctor 结果推断全站已就绪。

回退到不理解 revision 的旧 Core 前，先切回兼容的内置或 v1 安装主题。保留新增表和持久化版本，不自动执行删除历史数据的 down migration。Core 升级与首次接入遵守已有签名计划和维护窗口要求。

依据：[主题包现状](../site-themes/theme-packages.md)、[持久化存储](../../app/Support/Site/SiteThemePackageStorage.php)、[安装主题仓库](../../app/Support/Site/InstalledSiteThemeRepository.php)、[预览实现](../../app/Http/Controllers/Admin/SiteThemePreviewController.php)。

## 主站、托管站与外部渠道分别适配

| 目标 | 当前约束 | 升级策略 |
| --- | --- | --- |
| GEOFlow Laravel 主站 | 内置和安装主题，真实 Blade 渲染 | 完整远程草稿、文件、配置、预览、发布和回滚 |
| 第一方托管站 | 目前仅允许已认证的内置主题；安装主题预览拒绝托管上下文 | 增加按 revision 认证与绑定，检查站点内容隔离、路由、表单、素材、SEO 和分析；版本改变即需重检 |
| GEOFlow Agent PHP 目标站 | 独立渲染器，已支持能力协商、设置同步、静态模式和固定链接；无法直接运行 Laravel Blade | 新增受支持的展示数据、布局参数、CSS/JS 和素材版本协议，由 Core 转换并推送 |
| WordPress REST / Generic HTTP API 渠道 | 既有连接主要用于内容分发 | CLI 管理其已支持的内容和设置；完整站点模板编辑须有对方专用扩展，不纳入 GEOFlow 原生主题兼容承诺 |

### 托管站适配重点

认证绑定 revision 内容摘要和 Core 契约，避免只凭 manifest 自我声明就成为“认证主题”。站点隔离复用 `CurrentSite`、`SiteScopedArticleQuery` 和托管质量检查。主题读取、预览素材与发布 API 都验证 site_key，不能跨站点读取草稿或私有内容。

托管站启用开关、域名、DNS 和 TLS 是能力前提。功能关闭时返回具体原因；CLI 不自动修改宿主机或 DNS 配置。

### GEOFlow Agent 增量协议

新增能力 `presentation_revisions`，协议版本建议递增至 1.4，并保留 1.3 固定链接兼容。签名端点提供 prepare、asset transfer、validate、activate、status 和 rollback。Core 通过已有渠道签名客户端调用，用户的终端不持有渠道签名密钥。

目标站先准备完整候选，再切换展示版本；静态模式完成生成后切换 manifest。包含任务 ID、目标版本和幂等身份；超时先读取实际活动版本，部分站点失败按站点记录，不承诺跨站点分布式事务。渠道删除前继续检查操作租约。

Laravel 模板不会自动转换为等价的独立 PHP 目标站主题。可转换的首页模块、设计参数、素材和兼容布局由转换器处理；不支持的页面或模块在计划中明确列出并阻止声称“完全同步”。目标站 PHP 运行代码通过其软件发布升级，展示接口不承担任意运行代码部署。

现有旧目标包缺少新协议时，需要一次具备服务器权限的 CLI 部署升级；可以通过授权的部署工具完成，用户无需手工处理 ZIP。仅有旧版 GEOFlow 分发凭据无法凭空获得服务器升级能力。新安装目标站直接包含该协议，后续兼容的展示优化全部通过连接的 Core 和 CLI 完成。

## CLI 独立分发与跨平台执行

当前 `bin/geoflow` 依赖仓库根目录的 `vendor/autoload.php`，但其入口已经直接创建 HTTP 客户端，没有启动整个 Laravel 应用。这为独立打包提供了基础。

### 推荐交付形式

- 将现有 `app/Console/GeoFlowCli` 的客户端代码整理为可独立构建模块，复用现有 PHP/Symfony Console 与 HTTP 依赖。使用独立依赖清单和锁文件，仅打包客户端必需项及许可证，不直接封装整个 Core 的 vendor；不得加载项目 `.env` 或 Laravel 启动文件。
- 发布带所需依赖的 `geoflow.phar`、版本清单、SHA-256 与签名。运行目标固定为 PHP 8.3+，验收配置含 curl、mbstring、OpenSSL、Phar、fileinfo 和 sodium；无需 Composer、源码项目或本地数据库。安装入口检查这些条件并给出缺项。
- skill 提供一次性安装/更新入口，安装前验证来源与签名，保留上一版以便回退。正式源固定为项目官方发布，运行时不执行远端 metadata 中的代码。
- macOS、Linux、WSL 为首批验收平台。原生 Windows 沿用既有凭据 ACL 限制，验证合格后再宣称支持。
- 无 PHP 的平台需要先安装 PHP。将来可以评估自带运行时的单文件包，本轮保持现有技术栈，不额外引入 Go/Rust 客户端。

打包后的运行依赖通过干净环境 `--version`、`doctor` 和一次真实受控 API 调用确认，不能用开发机已安装依赖来替代安装验证。

签名校验从 A 的首个分发包开始交付。安装器和受信任公钥随正式 skill 包分发；使用固定 key ID 的 Ed25519 分离签名验证版本清单原始字节，再核对清单内的版本、文件名、SHA-256、大小及兼容范围，验证通过后才运行 PHAR。信任根不从待验证下载地址即时获取；换钥由已信任密钥签署过渡清单，根密钥失效时通过正式 skill 更新替换。自动更新拒绝降级，用户可显式回退到仍受信任的本地上一版本，profile 不被覆盖。

PHAR 自带摘要校验不能单独证明发布者身份；外部分离签名承担来源验证。PHP 配置只需允许读取 PHAR，运行用户无需关闭 `phar.readonly`。[PHP Phar 签名机制](https://www.php.net/manual/en/phar.setsignaturealgorithm.php)、[Phar 运行配置](https://www.php.net/manual/en/phar.configuration.php)。

首次使用仍需安装 skill、PHP 和 CLI；已有相应运行环境时直接复用。跨平台包说明必须列出这些实际条件，不能把可选截图检查器的 Node/浏览器依赖隐含为所有用户必装。

### CLI 的统一约定

| 方面 | 约定 |
| --- | --- |
| 目标选择 | `--profile` 或显式 `--config`；两者冲突时报错，保存 URL/token/实例身份的绑定 |
| 输入 | 保留已有 `--json FILE`；新增命令支持 `--input -`，秘密通过隐藏输入或 stdin |
| 输出 | 保留旧命令默认 JSON；新增命令默认 JSON，面向人工提供 `--output table`，错误也有结构化编码 |
| 结果位置 | 成功结果到 stdout，诊断到 stderr；详细日志仍脱敏 |
| 退出码 | 1.0 定义：0 成功、1 通用失败、2 参数错误、3 认证失败、4 权限不足、5 版本/幂等冲突、6 限流、7 异步等待超时、8 能力缺失、9 待对账 |
| 兼容策略 | 0.3 预览保留旧命令与退出码约定；改变旧行为时仅在 1.0 明确发布迁移说明 |
| 分页与范围 | 支持 cursor/page、fields 和有限查询；全量读取需显式选择，避免巨大内容进入模型上下文 |
| 超时与重试 | 保留 TLS 校验、重定向限制和响应限额；按错误码判断，不把 403 当登录过期 |
| 文件传输 | 逻辑路径、摘要、独立限额、流式资源；内部临时文件权限受控，结束后清理 |
| 执行续接 | 返回 workspace、operation、revision 与 request ID；后续对话可凭这些 ID 查询和继续 |

异步创建命令返回 0 仅表示受理成功，JSON 必须带 `accepted` 和状态；`--wait`/`operation wait` 在确认 `succeeded` 后才返回完成成功。等待超时不等于服务端取消，待对账使用专门状态和退出码。自动化调用者必须检查结果阶段，不能只凭初次退出码判断发布已完成。

0.3 保留已有秘密输入兼容，1.0 移除明文 `--password`/`--token` 参数并给出隐藏输入、stdin 和受保护配置的迁移方式。CLI 本地短期能力缓存和编辑片段在退出或过期后清理；未完成操作的非秘密续接索引保留至收据确认。token、个人线索、客户素材和实例地址不写入 skill 公共包、示例或评测快照。

### 需要保留与需要退场的内容

保留真实能力优先、身份绑定、幂等、预览与发布分离、只读回查、密钥脱敏和遗留兼容经验。把重复的 curl 实现、绑定完整工作区的远程 preflight、本地目录替换式线上操作从默认远程路径移除；需要时仅作为受限的旧版或源码开发工具。

skill 将远端文章、模板注释和检索内容作为数据处理。内容中出现“修改安全设置”“输出密钥”等文字，不能改变用户任务或命令权限。操作 schema 也只影响参数解释，不获得指挥 AI 执行本地代码的权力。

### 评测与发布条件

按 `yao-meta-skill` 的团队复用流程，验证 Skill IR、目标平台编译、触发与输出评测、Atlas/一致性、信任、打包安装、升级回退、漂移和 Review Studio。沿用现有 manifest 与报告，新增证据按需记录，入口保持简短。

2. 用同一 CLI 管理文章、任务、素材、站点配置，并执行至少一项异步生成和一项受保护操作。
3. 内置主题与已安装主题分别完成：远程建草稿、读取必要文件、修改布局/样式、在线预览、发布、第二轮修改、历史回滚。
4. 整个主题迭代不要求用户下载、解压或上传模板包；上传新图片由单资源命令完成。
5. 后台与 CLI 查看相同业务时，字段、权限、统计口径和最终状态一致。
6. Codex、新会话和另一个支持 Agent Skills 的终端环境，可凭 profile 与 operation/workspace ID 接续工作。
7. 断网、重复命令或两个编辑者同时操作时，不重复发布、不覆盖新版本、不把失败报告成成功。
8. 主站、两个托管站与兼容 Agent 分别验证主题和内容隔离；旧 Agent、未启用托管站有准确能力提示。
9. Core 更新、容器重建后，主题版本与当前绑定完整保留；回滚路径按方案演练通过。
10. 全后台覆盖台账没有未解释缺项，所有业务操作有注册契约和相应验证。
11. 首次 CLI 登录可以显式取得账号允许的新权限；旧登录行为不变，旧通配 token 不自动取得代码权限。
12. 一次发布改颜色，之后后台改广告：撤销前次发布保留新广告；同一个颜色项已被再次修改时，回滚返回冲突。
13. 写请求的整个响应丢失，再登录获得新 token：仍能按同一个客户端请求 ID 找到结果并避免重复执行。
14. AI 仅通过远程主题契约和必要文件片段完成修改；5 MiB 文本与二进制资源可按约定传输，不要求提高普通 JSON 上限。

## 方案取舍与失效条件

### 最小实现与推荐实现

最小实现可以先给现有后台操作补薄 API，再扩展 CLI，并支持首页模块与样式配置修改。它能减少后台点击，成本较低，但完整模板的持续迭代仍受当前安装模型限制。

推荐方案进一步引入服务端草稿和版本绑定，投入主要集中在主题与权限适配。它满足反复修改、多人协作、应用升级保留及回滚要求，减少长期人工处理模板包的成本。

| 其他方向 | 判断 |
| --- | --- |
| CLI 内部持续模拟后台表单 | 可短期适配页面，仍依赖会话、CSRF 和 HTML 结构；不作为正式管理协议 |
| 用户终端通过 SSH 直接编辑生产主题 | 需要服务器权限，容易与部署覆盖和并发编辑冲突；仅作为独立运维通道 |
| 新建 Node/Go CLI 完全替换现有 PHP 实现 | 增加客户端重写与多套契约成本；本次复用 PHP |
| 先建设独立 MCP 服务 | 增加每个平台的安装与连接配置；CLI + skill 已满足终端平台，MCP 可在未来复用相同 API |
| 建立通用远程代码执行或文件系统 API | 权限范围过大，也绕过业务规则；管理 API 只注册明确的领域操作 |

### 最脆弱的前提及处理

**本方案假定目标实例可以升级到新 API 契约，并具备可靠的持久化主题存储。** 如果实例无法升级，skill 只能执行它已暴露的能力；如果多副本没有共享存储，主题发布不能宣称具备一致性。

为此，doctor 与能力接口要报告升级条件、存储可用性和副本就绪状态；发布前验证必要条件。失败时保留当前绑定，返回明确缺项。

| 失效条件 | 系统行为与恢复 |
| --- | --- |
| Core/API 短暂不可达 | 保留本地 operation ID，恢复后查收据；写操作不盲目重试 |
| Core 完全宕机 | 使用既有宿主机 Updater CLI，远程 HTTP 客户端不能承担唯一恢复入口 |
| Agent 或 WordPress 远端不可达 | 保留每目标操作记录，进入失败或待对账；不回滚其他站点的独立成功记录 |
| 数据/文件规模扩大十倍 | 分页、增量、流式传输、队列和限额；发布事务仅切换小型记录 |
| 发布后新主题有问题 | 按已授权回切策略恢复，或生成历史版本回滚计划；业务数据独立保留 |
| 旧模板依赖不能识别 | 返回具体依赖和文件位置；补齐兼容声明或修改模板后再发布 |
| 管理员权限途中变化 | 后续 API、预览和作业停止使用旧授权，保留草稿和审计 |

### 所需凭据和部署条件

| 条件 | 用途 | 本次状态 |
| --- | --- | --- |
| 目标 GEOFlow 根 URL 与管理员登录方式或 token | 远程鉴权、权限与能力查询 | 用户尚未指定实例；设计完成不依赖读取其秘密 |
| 目标 PHP/队列/数据库和主题持久化存储 | 运行新增管理与主题能力 | 本地源码已核查，线上拓扑须在目标接入时验证 |
| 现有 AI 模型/搜索源配置 | 仅在执行生成、质检和可见性操作时使用 | 由目标服务器保管，无需复制到 CLI |
| 已有渠道签名密钥或第三方凭据 | 后台代理目标站和内容分发 | 继续由服务器保管；旧 Agent 另需一次部署授权 |
| 既有 Updater 接管及授权条件 | 在线更新、备份与恢复 | 复用既有 socket 和授权流程；具体实例未验证 |

| 可选独立浏览器检查器 | CLI 截图与视觉检查 | 非核心管理运行依赖；未安装时报告视觉验证缺失 |

本次已验证 GitHub 发布和源码读取可达，Laravel、OpenAPI 和参考项目公开文档可读取。拟议的新接口需实现后在测试实例验证；未宣称当前在线实例已提供这些接口。

## 确认与后续交付

建议确认本方案的五项决定，并优先实施 **A+B：独立远程 CLI、基础管理、主站模板在线迭代**。完整目标保持覆盖矩阵中的全部 Core 管理能力，再接入托管站和兼容 Agent。

建议版本安排为 Core 3.2 功能线、CLI 0.3 预览/1.0 稳定、skill 2.0；均为规划标识。每批按真实完成范围更新能力清单，只有全部验收通过后才对外宣称全面管理覆盖。

确认实施后，从最新 main 建立隔离工作区，重新检查基线漂移，按批次实现和验证，保留当前工作区状态。用户另行发出“提交”时，按项目规则完成审查、功能分支、PR、检查和合并；部署生产与正式版本发布按具体指令执行。

本方案已获确认并开始实施。当前预览版交付独立 CLI、连接权限、任务收据和主站主题草稿/预览；A+B 余项及 C/D/E 按覆盖台账继续推进。生产部署与正式发版另行安排。
